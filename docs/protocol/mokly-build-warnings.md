## Scope

A build warning is a non-fatal diagnostic raised while compiling a catalogue.
It reports ignored inputs or a structure that builds and works but degrades
accessibility or conformance, so the author can decide whether to change it. Warnings never
alter generated bytes, the manifest, HTTP responses, or timing records. This
contract defines the record, who produces it, which command reports it, and
the `--strict` option, including the exact warning lines. The broader terminal
presentation rules remain in the
[terminal output contract](./mokly-terminal-output.md).

## Record

```ts
type BuildDiagnosticCode =
  | "link-control-ancestor"
  | "link-control-descendant"
  | "removed-dependencies"
  | "removed-owned-dependencies"
  | "removed-shared-impact"
  | "duplicate-component-stylesheet"
  | "missing-configured-stylesheet-link"
  | "ignored-stylesheet-resource-owner";

type BuildDiagnosticSubject = {
  kind: "entry" | "component" | "folder" | "configuration";
  path: string;
};

type BuildDiagnostic = {
  code: BuildDiagnosticCode;
  message: string;
} & (
  | { route: string; subject?: never }
  | { subject: BuildDiagnosticSubject; route?: never }
);
```

- `code` is a stable kebab-case identifier that automation may branch on.
- `route` is the generated route of the document that produced the warning,
  relative to `mockupsDir/mokly-generated`, following the
  [generated artifact-path contract](./mokly-artifact-paths.md).
- `subject` replaces `route` for a warning that does not concern one page.
  Exactly one is present. Entry and component subjects use their complete
  resolved path, including a variant path. Folder subjects use the folder path
  (`""` names the root). Configuration subjects use the config file path relative
  to `repoRoot`, or its basename when that root is unavailable or does not contain the file. Paths use
  POSIX separators. A subject must not contain an absolute or traversing path.
- `message` is one line of plain text without the route or subject prefix.
  It does not repeat the subject.
- The printed subject is `<kind> <JSON-quoted-path>`, for example
  `entry "account/home"`, `component "ui/action"`, `folder "account"`,
  `folder ""`, or `configuration "tools/mokly.config.ts"`.

Raw C0 and C1 control characters are invalid in a diagnostic. Producers render
authored controls as visible lowercase JSON-style `\uXXXX` escapes before
normalization, and terminal reporters apply the same encoding defensively.

A compilation's diagnostics are sorted by their printed route or subject,
then `message`, then `code`, using lexical string comparison. A final subject-kind
tie-break (empty for a route) keeps distinct record identities. Duplicates
have equal code, route/subject and message. Existing route-only records keep
exactly their prior sort order. Ordering does not depend on the rendering
order, the operating system, or the absolute checkout path.

| Code                                 | Producer                                                   |
| ------------------------------------ | ---------------------------------------------------------- |
| `link-control-ancestor`              | A styled link control inside a warning-tier ancestor       |
| `link-control-descendant`            | A styled link control containing a warning-tier descendant |
| `removed-dependencies`               | Removed entry/variant fields; former folder declarations   |
| `removed-owned-dependencies`         | Removed component/variant ownership fields                 |
| `removed-shared-impact`              | Removed configuration field                                |
| `duplicate-component-stylesheet`     | Repeated real-file declarations on a component             |
| `missing-configured-stylesheet-link` | A missing configured placement anchor                      |
| `ignored-stylesheet-resource-owner`  | A renderer's stylesheet ownership record                   |

The tiers and message templates are defined in the
[styled link controls contract](./mokly-link-controls.md#placement-tiers).
The other messages belong to [authoring](./mokly-authoring.md#removed-input-warnings),
[folders](./mokly-folders.md#removed-input-warnings),
[configuration](./mokly-configuration.md#removed-review-setting),
[component stylesheets](./mokly-component-stylesheets.md#warning-messages), and
[stylesheet ownership](./mokly-component-stylesheet-ownership.md#ignored-owner-warning).
Future producers add a row here and define their own messages in their own
contract.

## Producers And Transport

The child-control adapter returns its adapted HTML together with the
diagnostics it raised. The direct document-link resolver returns its logical records
together with every document's diagnostics. The exhaustive compilation result
carries the sorted list as `diagnostics` beside the manifest and outputs, and
the on-demand single-document result carries the diagnostics of that document
beside its HTML. Referenced documents retain their own link-control diagnostics;
they do not become the requested document's diagnostics. Ignored-input producers
retain coverage of renders needed to validate its references.

Diagnostics are plain data. The background renderer's structured-clone message
carries them to the Serve parent unchanged. Configuration and registry producers
use the same record before rendering. The compilation includes their diagnostics
as well as render diagnostics. During exhaustive compilation, forward each
adapter's diagnostics through the compilation callback as soon as the adapter
returns, before logical-link rewriting and later resource validation. A
later validation or link-edit failure retains those warnings without inventing
a result. Keep the successful result sorted and deduplicate at the sink.
They are never written into generated files, never included in
`check` comparisons, never served over HTTP, and never uploaded.

## Reporting

Each command reports the diagnostics of exactly one compilation:

| Command         | Reported compilation                                          |
| --------------- | ------------------------------------------------------------- |
| `build`         | The compilation whose output is written                       |
| `build --watch` | Each complete compilation before its write                    |
| `check`         | The compilation whose bytes are compared                      |
| `export`        | The compilation that is packaged                              |
| `publish`       | The export's compilation, before any upload                   |
| `serve`         | Each generation's exhaustive compilation, once, when it lands |

Internal compilation callers have an explicit transport decision:

| Caller                     | Decision                                           |
| -------------------------- | -------------------------------------------------- |
| `build/compile_runtime.ts` | Preserve for the primary Serve generation          |
| `server/changed.ts`        | Discard secondary Changes evidence                 |
| `export/inputs.ts`         | Discard the final freshness comparison             |
| `review/run.ts`            | Discard; standalone Review has no warning reporter |
| `review/head_assets.ts`    | Discard direct-call head evidence                  |

Secondary compilations discard diagnostics: Changes evidence, export freshness,
and direct-call head evidence when accepted output was not supplied. Review has
no command reporter, and its compilation exists only for comparison evidence. `compileRuntime` is the exception among
internal callers because it is Serve's primary exhaustive compilation and
preserves diagnostics on its result. Baseline preparation captures a historical
tree's command output only for bounded failure diagnostics, so successful
warnings from that tree are not forwarded. Serve prints a generation's collected warnings
immediately before that generation's `Catalogue ready` boundary, in watched and
snapshot modes alike, and does not repeat them when a foreground request renders
one of the same documents on demand. Link-control warnings from ordinary
on-demand previews stay on their result until exhaustive compilation reports
them. Other producers also cover child-only and transient Props renders: unseen
current-attempt diagnostics can report after readiness. They use the same sink,
record, deduplication and reporters, never an independent warning channel.

One-shot commands print warnings after the rendering phase completes and before
the summary. Configuration, registry and render warnings discovered before a
failure print before the failure diagnostic. Without strict mode, a warning
never changes the exit status by itself. Secrets are redacted at presentation.

Plain reporters write exactly:

```text
[mokly/warning] <route>: <message>\n
```

Rich reporters write exactly the following unstyled text before terminal-width
truncation; supported terminals may style the surrounding presentation:

```text
  ! <route>: <message>\n
```

For a non-page subject, substitute the printed subject for `<route>` in both
lines. For example:

```text
[mokly/warning] entry "home": dependencies has been removed; ignoring it. Delete the field.
  ! entry "home": dependencies has been removed; ignoring it. Delete the field.
```

## Watched Serve Generations

Allocate a 32-character lowercase hexadecimal attempt identifier before startup,
rebuild or reconfiguration prepares inputs. Each producer captures that attempt.
Accepted runtimes retain it as `warningGeneration`, independently of the preview
cache `generation`. Reload, Git refresh and child restart do not reset it.

Branch-producer callbacks carry `{ generation, warning: BuildDiagnostic }`.
Children send `{ type: "warning", generation, warning }` through validated IPC;
background workers stream the same envelope to preserve warnings on failure.
The parent validates both the generation and diagnostic and owns the terminal.
A retained-config child never replays the parent's configuration diagnostics.
A full-manifest child captures its configuration attempt before config loading.

The sink accepts only the current attempt. Starting a newer attempt discards
pending older records immediately. Late background, completion and child records
cannot revive them, even when a failed attempt leaves old previews serving.

Successful completion combines the compilation diagnostics with already collected
records and prints each once, sorted, before `Catalogue ready`. Completion does
not add streamed records twice. Failure flushes that attempt before its failure
line. An older worker failure cannot flush a newer attempt's pending records.
A failed attempt retains its seen set; it never restores the older scope.
Unseen child-only or transient diagnostics after readiness/failure print once if
their attempt is still current. Reconfiguration uses the same rules on success
and failure. Snapshot Serve has one lifetime scope; one-shot commands have one
invocation scope. Historical build output and secondary evidence/freshness
compilations never enter these scopes.

## Strict Mode

`--strict` is accepted by `build`, `check`, `export`, and `publish` and refused
by `serve` with `cli-invalid` and the message
`--strict belongs to build, check, export or publish`. With `--strict`, a
command counts every producer, still prints every warning, then fails with `build-invalid` and the
message `1 build warning with --strict` for one warning or
`<n> build warnings with --strict` otherwise. This failure is the immediate
next action after reporting: `build` fails before `outputStore.write`, `check`
before tracking/comparison, `export` before capture or staged export bytes are
written, and `publish` before bundle capture or upload. The last-good generated
and export trees therefore remain unchanged. Without warnings, `--strict`
changes nothing. Watched Build applies this check before every write. A rejected
compilation preserves the last-good tree and reports the error through the
existing watch failure path; watching continues so the author can repair it.
Only explicit writers take the generated-output lock; warnings add no reader lock.

## Verification

Unit tests cover record validation and sorting, both reporter line formats, and
option acceptance per command. Compile-level tests prove a warning-tier
structure builds identical bytes with one sorted diagnostic on the compilation.
CLI-level tests run `build` and `check` through the in-memory terminal and
assert the plain stderr line, unchanged stdout, exit `0`, and the strict
failure. A Serve test proves one report per generation and none per on-demand
request.
