# Mokly Contract Fixtures

The workspace CLI owns the generated bytes. The generator uses its public
commands and file artifacts. It imports no private Mokly module.

Install with `npm ci` and build with `npm run build`. Run these commands from
the repository root:

```sh
node xtask/scripts/mokly-fixtures.mjs
node xtask/scripts/mokly-fixtures.mjs --check
cargo xtask mokly-fixtures
cargo xtask mokly-fixtures --check
```

The Node command regenerates all golden files. Check mode compares every byte
and file name. It then runs the corpus, both captured indexes, and the published
`catalogue-v9.json` through the public `readCatalogueIndex` of `@mokly/viewer`.
The xtask command also runs the Rust consumer smoke test.

## Frozen Sources And Captured Plans

`src/` holds native HTML screens, a registered HTML component, a page, a
Markdown document, and a YAML use case. Its data-only `mokly.config.json`
selects these files. Native authoring keeps render input keys independent of
the absolute source root. The released React authoring path produces different
`documentKey` values at different roots. The xtask mockup smoke test still uses
that React API.

The original catalogue has screens `start` and `finish`, component `notice`
and variants `notice/draft` and `notice/published`, page `page`, document
`guide`, and use case `publish`. Between two fixed commits, the generator edits
the component body, the start heading, the use-case step title, the page body,
the document body, and the `.notice` CSS rule. Every kind has direct Changes.
The component detail lists `finish` as affected, while Changes excludes it.

`moves/src/` holds common JSON configuration and separate baseline and current
catalogues. It covers declared and inferred moves, the case-only rename
`Account/Kept` to `account/kept`, dark views, removed screens, pages, documents,
component parents and variants, and variants moved to another parent. It also
keeps parent-to-variant and variant-to-parent shape changes. Mokly has no removed
use-case record.

The generator commits source only with the fixed identity and date in the
[fixture procedure](../../../docs/protocol/cloud/mokly-fixture-regeneration.md).
Native fixture checkouts need no package manifest or dependency symlink. The
generator uses the workspace CLI and viewer of the root npm workspace.
Each comparison uses `HEAD~1`. `build --strict
--out .context/export` writes the complete export. `publish --strict` sends a
Plan to a loopback receiver. The receiver checks the test bearer and refuses
that one request with 426. No external service receives an upload.

The Plan marker must declare the build's entire inventory unchanged, plus
`mokly-upload.json`. The generator verifies the captured workspace version.
It replaces the client time and release number with fixed values, then updates
the envelope's marker digest and size. It preserves all other
producer JSON bytes. CLI processes use private cache and temporary directories.
The generator checks the printed locations and removes retained publish builds.
It removes its whole temporary root on exit.

The pinned npm `tar` writes portable USTAR/PAX archives with epoch times and
mode 0644. Each complete export stays below 640 KiB. The generator refuses
unexpected files. Only the README, source trees, corpus, and its two Node
modules are authored inputs.

Consumers read the fixture producer version from `checksums.json`.
The recorded placeholder is independent of the workspace package version.

## Index Changes-Count Corpus

`index-v9-cases.json` is an authored, language-neutral schema-1 corpus. It has
one `baseDocument` and `cases`, with no package release numbers.
A corpus edit requires fixture regeneration.

Each case has a unique `name` and one input form:

- `patch`: JSON Pointer operations with `op: "set"` and `value`, or `op:
"remove"`. An empty pointer replaces the root. Array removal closes the gap.
- `rawDocument`: exact UTF-8 text for duplicate keys and the BOM.

`index-corpus.mjs` renders patched inputs with recursively sorted UTF-16
object keys, array order unchanged, no spaces, and no final newline. Each case
has `documentSha256`. Both harnesses check it before decoding. Raw inputs
keep their exact text bytes. The Rust harness runs in
`tests/compatibility/corpus_tests.rs` through `CatalogueIndex::parse`.

An accepted case has `counts: { changed, added, removed, moved }`. The Node
check derives these counts from the value that `readCatalogueIndex` returns.
It counts only ready, included records. Each current kind and each variant
counts once. Removed records count once. `changed` and `unmodified` enter the
changed bucket. Moved entries also enter the moved subset.

A rejected case has `cloudRejection: "invalid"` for 400, or
`"unsupported-version"` for 426. It also records `viewerValid`. Duplicate-key
cases have `viewerValid: true`, because the public reader receives parsed
objects. The public reader checks only the version and copies content.
Every cloud-accepted case must pass that reader. Cloud content rejections
remain unchanged. The corpus
covers the read-field checks in
[Publication index](../../../docs/protocol/cloud/publication-review.md).

`check-index-corpus.mjs` runs as an ESM entry from the repository root so that
the public package resolves through the root npm workspace. The generator invokes it in
check mode. It reports the case name for a hash, count, or viewer mismatch.

## CLI Failure Codes

`cli-errors.json` records placeholder `moklyVersion: "0.0.0"` and ordered rows with `scenario`,
observed `code`, and observed `exitCode`. The private checkout probes:

- `uncommitted-file`: `git-uncommitted`, with no upload request.
- `refused-upload`: `upload-failed`, after five authenticated Plan POSTs to a
  loopback receiver that answers 503 with `Retry-After: 0`.

The generator records the actual plain stderr code without requiring a fixed
code value. A renamed code changes the fixture and its checksum. Check mode
repeats both probes. The CLI has no stale-output scenario or review file.
