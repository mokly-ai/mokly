# Chromium install wait can block a shard for an hour

- **Severity:** Medium. **Effort:** Small. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Outside the scope.
- **Added:** 2026-11-26, from the branch `calummoore/ci-speed-flaky-follow-ups-b-and-new-k3dt`, its pull request CI.
- **Location:** `.github/workflows/ci.yml:291-311`, the steps "Start Chromium install" and "Wait for Chromium install", which the browser shards and the other Chromium jobs share through YAML anchors.
- **Reason:** The branch does not change `ci.yml`, and the source of the hang is unknown, because the wait printed no log.

- **Source:** Implementation.
- **Category:** Test.
- **Terms:**
  - **Background install:** "Start Chromium install" opens `$RUNNER_TEMP/chromium-install.lock` as file 9, locks it, and starts `npx playwright install --with-deps chromium` with `nohup` in the background. The background shell keeps the lock until it writes the exit status and ends.
  - **Install wait:** "Wait for Chromium install" runs `flock "$RUNNER_TEMP/chromium-install.lock" true`, then prints the install log and checks the status. It has no time limit of its own.
- **Background:**
  - Pull request #535 and #537 of 2026-11-25 moved the Chromium install into the background, so that it runs while "Build native and JavaScript packages" builds.
  - CI run 45749948941 of pull request #550, commit `bec7133a3`, on 2026-11-26: the job "Browser (Node 22.15.0, shard 14/14)", job 139675090032, entered the install wait at 03:38:00 UTC. It made no output until the 60-minute job timeout cancelled it at 04:36:23 with "The operation was canceled.". The "Required CI" job then failed. The other 13 browser shards passed.
  - The wait never reached its `cat`, so the log of the install, with the apt and download output, is lost.
  - In the 47 CI runs from #537 to 2026-11-26 04:40 UTC, this is the only job that stopped in the install wait. The 61 other cancelled Chromium jobs ended by concurrency cancels.
  - The rerun of the failed jobs of run 45749948941 started at 04:40 UTC.
- **Problem:** When the background install stops making progress, the wait blocks until the job timeout and shows no cause.
- **Impact if no action:** A shard can hold a runner for an hour and fail the required check, now and then, with no evidence for a fix.
- **Root question:** How does a shard learn that the background Chromium install stopped, and why it stopped?
- **Options:**
  - **A.** Wait with `flock -w {seconds}` at three times the typical install time. When the wait ends without the lock, print the install log, the process tree, and the apt locks, and fail the step. It adds a time limit to a step, so it needs the user. Effort: Small.
  - **B.** Write the install output to the job log as it runs, for example with a `tail -f` of the log in the wait step until the lock frees. A hang then still lasts until the job timeout, but the log shows the last output. Effort: Small.
  - **C.** Run the install in the foreground again. The cause then shows in the job log, but each shard loses the time that the background install saves. Effort: Small.
- **Left out:** A retry of the install, because it hides the cause, and the testing rules rule it out without the user.
- **Wider fix:** None until the cause is known.
- **Previous examples:** None found.
- **Recommendation:** B. It keeps the time saving and gives the evidence of the next hang without a new limit.
- **Action:** ask the user, because the source is unknown and option A adds a time limit.
