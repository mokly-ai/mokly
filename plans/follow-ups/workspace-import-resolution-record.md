# Each import path rebuilds workspace resolution facts

- **Severity:** High. **Likelihood:** Rare. **Effort:** Large. **Confidence:** High. **Harder later:** Yes.
- **Kind:** Fix after merge.
- **Added:** 2026-11-26, from the wider fixes of findings 40, 41, 2, 4, 80, and 83 of round 1 and of findings 130, 131, 132, 160, and 161 of round 2 of the review of branch `calummoore/mokly-source-package-override-jkum`.
- **Location:** `resolveImport`, `resolveRequire`, and `retryRequire` in `packages/mokly/src/sidecar/importer-resolution.ts`, `workspacePackage`, `workspaceTarget`, and `workspaceImport` in `packages/mokly/src/sidecar/workspace-imports.ts`, `ModulePaths.resolve`, `ModulePaths.resolveSync`, and `ModulePaths.missing` in `packages/mokly/src/sidecar/module-paths.ts`, `planNative` in `packages/mokly/src/sidecar/native-plan.ts`, `ConfiguredModuleFiles.has` in `packages/mokly/src/sidecar/module-configured-files.ts`, `WorkspaceSources.packageRoot` in `packages/mokly/src/sidecar/workspace-sources.ts`, `packages/mokly/src/sidecar/postcss-module.ts`, `packages/mokly/src/sidecar/postcss-resolution.ts`, `packages/mokly/src/sidecar/postcss-require-target.ts`, `packages/mokly/src/sidecar/postcss-path-hooks.ts`, `packages/mokly/src/sidecar/postcss-preload.ts`, `crates/mokly-css/src/resolver.rs`, `crates/mokly-css/src/workspace_sources.rs`, and `crates/mokly-compare/src/ignored_modules.rs`.
- **Reason:** The record changes every workspace lookup path, also for detected packages and in the Rust CSS resolver, beyond the purpose of the branch.

- **Source:** Review.
- **Category:** Code structure.
- **Terms:**
  - **Head and base:** The head is the render of the working tree. A base is the render of the files of a Git commit, which Changes compares with the head.
  - **Workspace package:** A package whose `package.json` and files are in the repository, outside `node_modules`.
  - **Layout order:** The folder layouts that a side tries, in order, to map a built file of a workspace package to its source file. The "Layout Order" section of `docs/protocol/mokly-comparison-packages.md` defines it.
  - **Declared target:** The path that the `exports` or main field of a package names, before Mokly resolves links.
  - **`ignored-module` warning:** The warning that Mokly gives, when Changes runs, for each repository file that the head loads and Git ignores.
- **Background:**
  - Four paths resolve a workspace import:
    - bundled imports through esbuild
    - requires that Node loads
    - PostCSS plugin loads and their bundles
    - CSS `@import` in the Rust CSS resolver
  - The consumers of an import need some of the same facts:
    - the side, head or base, whose files the import must use
    - the written path, which is the path that the load names, such as a link, before Node follows links
    - the declared target
    - the canonical file, which is the real path that Mokly reads and records
    - the import form: a package name, a relative path, or a require that Node loads
    - the available fallback, which tells whether the layout order gives a source file on that side
  - The consumers are the layout lookup, the reuse evidence, the failure hints, and the `ignored-module` warning. Each path derives the facts that its consumers need, apart from the other paths.
  - Round 1 of the review of this branch found six defects of this class. The branch fixed each one where it occurred, on 2026-11-26:
    - **Base imports used the working export.** A base exported `old-build/old.js` and the head exported `new-build/new.js`, with matching layouts on both sides. The base failed on `new-build/new.js`, because native lookup read the package through the link of the working installation. With a base `false` entry, an existing base build also failed when the working build was absent. The fix looks the package up again in the side's own package folder when its `package.json` differs from the installed copy. The CSS resolver now checks a kept target under the side's package root.
    - **A linked build folder skipped the layout in JavaScript.** With `esm` linked to `release` and the entry `{ "esm": "source" }`, a JavaScript import loaded `release/skin.css`. A CSS `@import` of the same export loaded `source/skin.css`. The sidecar resolved the link before it matched the build folder. The fix passes the declared target whose real path equals the native result to the layout lookup.
    - **The warning skipped relative requires.** The warning skipped every require that Node loads, because it assumed that a base recovers the source. Recovery covers only imports by package name, so an ignored `generated/plugin.cjs` that a relative require loaded got no warning. The fix sends the modules that Node loads as evidence, and it marks each one that Mokly's require reached by package name. The check skips only a marked module whose layout gives a source that Git tracks or does not ignore.
    - **A relative import got a useless hint.** The warning and the failure messages named `moduleResolution.sourcePackages` for any file in a workspace package. No entry can change a relative import such as `./packages/theme/esm/skin.css`. The fix names the setting only for an import by package name of a target below a package subfolder. A `false` entry that ends the layout order also removes the hint.
    - **Bundled PostCSS plugins escaped the warning.** The PostCSS bundler dropped the entry file of each bundle from its import evidence. The PostCSS configuration can name a workspace plugin in record form, or load it by a computed import. Such a plugin enters the bundler as an entry, so its ignored build file got no warning. The fix gives the bundler an explicit entry role.
    - **Stylesheet records repeated the PostCSS import list.** The worker returned its cumulative `bundledImports` list with each stylesheet, and each cached record kept a copy. For 400 records that share 500 paths of 80 bytes, the copies add about 79 MiB to a cache of 64 MiB. The fix replaced the list with a tag on the `plugin_inputs` entry of each file that a PostCSS bundle reached.
  - Round 2 of the review found five more defects of this class. The branch fixed each one where it occurred, on 2026-11-26:
    - **The base followed the build link of the working tree.** Both manifests exported `./esm/value.cjs`. The working tree linked `esm` to `release`, and the base tracked a regular `esm/value.cjs`. Equal manifests kept the lookup in the working installation, so the base used the working destination `release/value.cjs` for its fallback and its file check. The base then failed with `module packages/local/release/value.cjs has no source in this side`, or it loaded the wrong file. Commit `d22a5fe82` keeps a build from the real path of the declared target on the side of the import. It counts identical declared targets as one match.
    - **A package import replaced a configured module.** A configured `packages/ui/release/renderer.js` was also exported as `./esm/renderer.js`, through an `esm` link to `release`. With `esm` mapped to `source`, the package import checked the written `esm` path against the configured files. It missed the configured file and selected `source/renderer.ts`, so one bundle held two copies of the renderer. A detected layout gave the same result, with `dist` linked to `release`. Commit `d22a5fe82` makes `ConfiguredModuleFiles.has` compare real paths on the render side.
    - **Serve missed a new package manifest.** A package exported `./nested/dist/value.js`, with `nested/dist` linked to `../release`, and `nested/src/value.ts` existed. A new `nested/package.json` with a name changed the file that a fresh compile selects. Serve reuse kept the old module, because the detection found no build folder and recorded no manifest probes. The ancestors of the consumed real file also exclude `nested/package.json`. Commit `d22a5fe82` records each `package.json` that the package root search reads, also without an entry.
    - **A package require hid an exact PostCSS load.** The PostCSS configuration loaded an ignored `packages/theme/esm/plugin.cjs` by package name and by a computed relative path. With `{ "esm": "source" }` and a tracked `source/plugin.js`, the package mark won in either call order. So the warning was missing, though a later base fails on the relative load. Commit `3abb22eff` counts every Node load. It marks a file as a package require only when every load of the file was Mokly's require by package name.
    - **PostCSS lost the paths for the Git check.** A computed relative require of an ignored link to a tracked `.cjs` file reported only the tracked target. The warning was missing, and the base failed with `MODULE_NOT_FOUND`. A package require through an `esm` link to `release` reported `release/plugin.cjs`. The layout `{ "esm": "source" }` cannot map that path, so the check gave a false warning. Commit `3abb22eff` makes Mokly's PostCSS require report the written path of an exact load and the declared target of a package load.
  - Two PostCSS load sites still report only the canonical file: the PostCSS bundler in `postcss-module.ts`, and the hook for native requires in `postcss-path-hooks.ts`, which records the `filename` of the loaded module. So a bundled import or a native `createRequire` through an ignored link to a tracked file gets no warning. A read of the code shows this, and nobody ran these cases.
  - The record keeps the behaviour that the protocol pages state, so it needs no protocol change.
- **Problem:** Each path derives part of the facts of a workspace import on its own. One consumer can then lose or misread a fact that another path already holds.
- **Impact if no action:** Each new consumer, such as a new hint or a new evidence list, must derive the facts again and can repeat these defects. The result is a wrong file, a useless hint, or a missed warning, and a missed warning can cost Changes in a later pull request.
- **Root question:** How does every consumer of a workspace import read the same facts about how that import resolved?
- **Options:**
  - **A.** Keep the eleven fixes of 2026-11-26 where they are. Each later consumer derives the facts that it needs, and a review must check each one. Effort: Small.
  - **B.** Build one resolution record in the sidecar only. `resolveImport`, `resolveRequire`, and the PostCSS loaders return it, and the evidence that the sidecar sends to the core carries it. The Rust CSS resolver keeps its own derivation, so CSS and JavaScript can still disagree. Effort: Large.
  - **C.** Build one resolution record for each workspace import, in the sidecar and in the Rust CSS resolver. It holds the side, the written path, the declared target, the canonical file, the import form, and the available fallback. The failure hints, the reuse evidence, and the `ignored-module` warning read only the record. Effort: Large.
    - Take the side fact from a lookup in the side's own package folder. For a workspace package that the base reaches through the working installation, always repeat the package lookup there, and drop the manifest comparison. When that lookup gives the same mapped file, keep the native compile exact, so that its result still stands. `planNative` in `packages/mokly/src/sidecar/native-plan.ts` decides when a native compile is exact. Test equal manifests with and without a working link, for the bundle and for the restored require. The review of 2026-11-26 proposed this part for the base that followed the working link.
    - Report the written path at every PostCSS load site: Mokly's require, the PostCSS bundler, and the hook for native requires, in the worker and in `postcss-preload.ts`. Keep the form of each load, so that an exact load wins over a package load of the same file. Send one dependency entry for each load form, and remove the merges in the worker. The import kind order of the core is then the only merge rule. Add a CLI case for each site. The review of 2026-11-26 proposed this part for the lost PostCSS paths and for the hidden exact load.
- **Left out:**
  - Dependency views with workspace links to the files of each side. They fix only the side fact, and they add setup and cleanup to each base.
  - A table of import forms and outcomes that both copies of the rule run. It finds a difference between the copies, but each consumer still derives the facts.
- **Wider fix:** C. One owner keeps the written path, the package selection, the path mapping, the import form, and the fallback together, so no consumer derives them again.
