# First latest desktop release is not proven

- **Severity:** Medium. **Effort:** Small. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Post-merge task.
- **Added:** 2026-11-24, from the post-merge task of the deleted plan `plans/desktop-full-latest-releases.md`, on the branch `calummoore/desktop-releases-become-latest-releases-clkn`.
- **Location:** `.github/workflows/desktop-release.yml`, the `release` and `promote` jobs. `packages/desktop/scripts/release-promote.mjs`, with the check of GitHub's latest version. `packages/desktop/scripts/release-build-record.mjs` and `packages/desktop/scripts/release-assets.mjs`, the build record and the rerun reuse by digest. `packages/desktop/src/updates.ts`. The sections "Latest Release" and "Drafts And Promotion" of `docs/protocol/cloud/desktop-distribution.md`.
- **Reason:** Only a real desktop release runs the draft, the promotion, the latest mark and the GitHub asset digests. Only a real rerun reads the build records of earlier attempts. Both run only after the merge.

- **Terms:**
  - **Draft:** A GitHub release that only repository collaborators can see. It is not in the release feed and is never GitHub's latest release.
  - **Promotion:** The `promote` job. It checks the complete assets of both platforms, then makes the draft a full release that GitHub marks as latest, unless a higher version is already latest.
  - **Fixed latest address:** `https://github.com/mokly-ai/mokly-desktop/releases/latest/download/{name}`, where `{name}` is an asset name without a version, such as `Mokly-mac-arm64.dmg`.
  - **Build record:** A JSON file that each attempt of a platform job writes before any upload. It holds the tag, the platform, and the name, size and SHA-256 hash of each built file. The workflow uploads it as the artifact `desktop-build-record-{platform}-{attempt}`, where `{attempt}` is the number of the run attempt, and keeps it for 35 days.
  - **Digest:** The `digest` field of a GitHub release asset: `sha256:` and the SHA-256 hash of the stored file.
- **Background:**
  - On 2026-11-24 the owner chose full desktop releases. Each release is created as a draft. Both platform jobs fill the same draft. The promotion makes it the latest release only after the complete asset check. A later change adds a download page on mokly.ai that links the fixed latest addresses.
  - On 2026-11-24 the owner also answered two review items of the same change. First, a late promotion must not move the latest mark backward. Before publication, the promotion reads GitHub's latest release. When that release has a higher version, the promotion does not publish, the release stays a draft, and the job passes with a warning that names both versions. A 404 counts as no latest release. Second, a complete draft must not get stuck after a late failure. A rerun of a platform job that finds the complete fixed set of its platform on the draft uploads nothing. It passes only when the digest and the size of each asset match a build record of an earlier attempt. A partial set still fails, and the release then needs a new version.
  - The rerun reuse depends on two GitHub behaviours that only a real run shows. The step "Download earlier build records" of the `release` job must receive the build records of the earlier attempts of the same run through `actions/download-artifact`. GitHub must also return a digest for each release asset. When either fails, a rerun after a complete upload fails, and the release needs a new version.
  - The installer names hold no version since the same change. The fixed names are `Mokly-mac-arm64.dmg`, `Mokly-mac-x64.dmg`, `Mokly-mac-arm64.zip`, `Mokly-mac-x64.zip`, the four matching `.blockmap` files, `latest-mac.yml`, `Mokly-linux-x86_64.AppImage`, `Mokly-linux-amd64.deb` and `latest-linux.yml`.
  - Unit tests prove the draft check, the build record, the rerun reuse by digest, the promotion check with its latest version check, and the GitHub client with test doubles. The pull request packaging job checks that each platform builds exactly the fixed file names. No test calls GitHub.
  - electron-publish 26.18.0 returns a matching draft from the release list before any other check. So the Linux job should reuse the draft that the macOS job created. Only a real release proves it.
  - Before the change every release was a pre-release, and `GET https://api.github.com/repos/mokly-ai/mokly-desktop/releases/latest` returned 404. The newest release was `v0.1.0`, with versioned names such as `Mokly-0.1.0-mac-arm64.dmg`.
  - New builds set `allowPrerelease = false`. electron-updater then reads `https://github.com/mokly-ai/mokly-desktop/releases/latest`. Installed `0.1.0` apps keep `allowPrerelease = true`. With a version that has no pre-release part, they take the first entry of `releases.atom`. That feed listed the newest published release first on 2026-11-24. A promoted draft gets a new publish time, so it should be the first entry.
  - electron-updater 6.8.11 builds the old blockmap address from the new file address. It replaces the new version with the old version. From `0.1.0` that address names a file that does not exist, such as `v0.1.0/Mokly-mac-arm64.zip.blockmap`. The 404 makes the updater fall back to a full download.
  - `DESKTOP_RELEASES_TOKEN` is a fine-grained token with Contents write on `mokly-ai/mokly-desktop` only. GitHub's release update endpoint needs Contents write, so the promotion needs no new scope.
