# The template probe skips Git's Perl patterns

- **Severity:** Medium. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-26, from the branch `calummoore/builds-keep-the-template-s-compiler-and-csnm`, as part of the item "No check keeps the template's compiler". On 2026-11-26 finding 12 of review round 4 of the branch `calummoore/builds-spike-a-plain-debian-base-for-the-aa76` restored its Git part under this name.
- **Location:** `infra/e2b/tests/assert_build_template.py`, `verify_git_base_reads`, whose Git checks stop at the version and `git cat-file --batch --filters -Z`; `infra/tests/test_build_template.py`, `fake_git` and its two Git regressions, `test_git_without_cat_file_nul_batches_fails` and `test_git_2_43_or_newer_with_cat_file_nul_batches_passes`; `docs/protocol/cloud/cloud-build-template.md`, sections "Tools" and "Candidate Assertion"; `docs/ops/build-template.md`, section "Template Releases"; `xtask/src/policy/build_pins.rs`, beside `e2b_base`.
- **Reason:** Each option except A adds a release step, a probe rejection, or a lint, which only the user approves.

- **Source:** Review.
- **Category:** Process.
- **Terms:**
  - **Build template:** the E2B sandbox image, `mokly-build-v<N>`, in which Mokly Cloud runs the checkout, the install, and `mokly publish` of a customer repository. `infra/e2b/build/e2b.Dockerfile` defines it.
  - **Template probe:** the live check of `docs/ops/build-template.md` that runs `infra/e2b/tests/assert_build_template.py` in a fresh sandbox of a candidate build reference before an operator enables it.
  - **PCRE2:** the library behind Perl-compatible patterns in Git, such as `git grep -P`, `git log -P`, and `grep.patternType=perl`.
- **Background:**
  - On 2026-11-26 Cal decided the template contract of `docs/protocol/cloud/cloud-build-template.md`. Its section "Tools" says that the template supplies Git 2.43 or newer, which supports Perl-compatible patterns in `git grep -P`.
  - The probe checks only that the `git` on `PATH` reports 2.43 or newer and accepts `git cat-file --batch --filters -Z` on empty input in a new repository. It runs no `git grep -P`.
  - The same day, Cal decided the toolchain part of the earlier item. The contract names the C and C++ toolchain with `ar`, `ld`, `make`, `pkgconf`, and `libtool`. The probe builds and runs a small C and C++ program, and it runs `pkg-config` and `libtool`. Release `mokly-build-v8` installs `pkgconf` and `libtool`. That decision added no Git pattern check, so this item keeps only the Git part.
  - Release `mokly-build-v5` (2026-11-26) built Git 2.56.1 from source without PCRE2. `git grep -P` with a real Perl pattern exits 128 there. Its recorded probe pass did not show the loss, because the probe runs no Perl pattern.
  - Release `mokly-build-v6` (build reference `mm5vcm4xv7inkey7ad9p:e58c1440-c5e2-406d-97a3-8d312416c61c`, 2026-11-26) built that Git with `USE_LIBPCRE2=1`. In a v6 sandbox, `git grep -P` with a Perl lookahead worked. Main-preview uses v6 since 2026-11-26.
  - Releases `mokly-build-v7` and `mokly-build-v8` use Debian trixie's Git 2.47.3 at `/usr/bin/git`. The v8 release checks matched a lookahead with `git grep -P` in a sandbox of the build reference `gwdwriayx6ky1a5n5lfc:635dd814-a8b5-41aa-87be-05ea3d74a291`. Those checks ran beside the probe, not in it. Cal switches main-preview from v6 to v8 after the v8 Dockerfile merges into `main`.
  - A plain-text pattern, such as `git grep -P 'Mokly'`, also matches without PCRE2. `git grep` exits 0 on a match, 1 on no match, and 128 on a fatal error, such as a Perl pattern in a Git without PCRE2. So a check needs a pattern that only a Perl engine accepts, and it must require exit 0 and the expected line.
  - The probe requires exactly one real `git` file on `PATH`, so a second Git beside Debian's fails it. A single Git that replaces Debian's, or a new base whose Git lacks PCRE2, still passes.
  - Mokly and the cloud runner use no Perl patterns in Git. Only customer code meets the gap: install lifecycle scripts, and base-install scripts when the repository enables them.
- **Problem:** The contract promises Git with Perl-compatible patterns, but the probe does not check them. A later release can lose PCRE2 while the probe passes, as v5 did.
- **Impact if no action:** A customer script that uses `git grep -P`, `git log -P`, or `grep.patternType=perl` then fails in cloud builds with exit 128, while it works in the customer's own CI. The failure shows as a Git error, not as a template problem.
- **Root question:** How do later template releases keep the Git Perl-pattern support that the contract promises?
- **Options:**
  - **A.** Keep this item only. The contract states the promise, and only the release smoke checks run `git grep -P`. No check enforces the promise. Effort: Small, already applied.
  - **B.** Add a Perl-pattern smoke step to each release record in `docs/ops/build-template.md`. The operator runs `git grep -P` with a lookahead in a sandbox of the full build reference, `TEMPLATE_ID:BUILD_ID`, and records the result with that reference. A release can skip this manual step. Effort: Small.
  - **C.** The probe commits a tracked file in its temporary Git repository. Then it runs `git grep -P` with a pattern that only a Perl engine accepts, such as a lookahead, and it requires exit 0 and the expected line. Exit 1 means no match, and exit 128 means a Git without PCRE2. Add a regression in `infra/tests/test_build_template.py` for a Git that reports a supported version and fails the match. Add the check to the section "Candidate Assertion" of `docs/protocol/cloud/cloud-build-template.md`. The probe changes after the v8 pass, so v8 needs a new probe run. Effort: Medium.
  - **D.** Add a `toolchain-pins` rule beside `e2b_base` in `xtask/src/policy/build_pins.rs`: the template takes Git only from Debian's `git` package. It rejects a Git source build or another Git install in the Dockerfile. It does not prove PCRE2 in the built image. Effort: Medium.
  - **F.** Add a rule to `docs/protocol/cloud/cloud-build-template.md`: the probe uses each tool and feature that the page names, not only its version. Each such check has a regression in which only that tool fails. It covers the class: the v2 probe ran only `npm --version`, and the v5 probe ran no Perl pattern. The probe's other version-only checks, such as curl and corepack, then also need working checks, and a working corepack check needs the network. Effort: Medium.
- **Left out:**
  - Drop the Perl-pattern promise from the contract. It breaks a requirement that Cal decided on 2026-11-26.
  - A check with a plain-text `-P` pattern. It also passes without PCRE2, so it fails the goal.
  - A different Git source, such as a source build with `USE_LIBPCRE2=1`. It changes how the template gets Git, not how a release keeps the feature, and on 2026-11-26 Cal chose Debian's Git.
- **Wider fix:** F. The rule makes each promised tool and feature a working check, so a probe cannot pass a release that lost one.
- **Previous examples:** `mokly-build-v2` broke npm while `npm --version` passed the probe. The fix added a real `npm ci` to the probe. `mokly-build-v5` lost PCRE2 in its Git while the probe passed.
- **Related:**
  - `plans/follow-ups/build-template-rollback-has-no-verified-target.md`: a rollback target must pass the current probe. With C, a release whose Git lacks PCRE2 no longer qualifies.
  - `plans/follow-ups/template-probe-pass-not-tied-to-assertion.md`: C changes the probe after the v8 pass. That item asks how each enabled build reference gets a pass of the new assertion.
- **Recommendation:** C. It checks the promised feature in the probe that each release and each rollback target must pass. F best protects the codebase.
- **Action:** ask the user, because B, C, D, and F add a release step, a rejection, or a lint.
