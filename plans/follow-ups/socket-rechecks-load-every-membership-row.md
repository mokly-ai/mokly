# Socket rechecks load every membership row

- **Severity:** Medium. **Effort:** Medium. **Confidence:** High. **Harder later:** Yes.
- **Kind:** Fix after merge.
- **Added:** 2026-11-25, from the implementation review of the branch `calummoore/live-channel-foundation-implementation-n1hi`, finding 8. Its finding check added options D and E, and it named D as the wider fix.
- **Location:** `crates/mkc-api/src/platform/project_access.rs:19-46` (`ProjectReader::read`), `crates/mkc-api/src/builds/reads.rs:20-28` (`member_role`), `crates/mkc-api/src/live/access.rs:51` and `:72`, `crates/mkc-store-pg/src/member.rs:89` (`members`), and `crates/mkc-store-pg/src/grant.rs:82` (`grants`). Option D also reaches `crates/mkc-api/src/platform/policy.rs:20`, `crates/mkc-api/src/github/policy.rs:24`, `crates/mkc-api/src/billing/read.rs:22`, `crates/mkc-api/src/billing/checkout.rs:95` and `:144`, `crates/mkc-api/src/billing/portal.rs:27`, and `crates/mkc-publications/src/policy.rs:86`.
- **Reason:** The fix changes the project access lookup that every REST project read shares, and its store queries, outside the live channel work.

- **Source:** Review.
- **Category:** Performance.
- **Terms:**
  - **Live socket:** the WebSocket that the app opens for each project that a member reads, on `GET /v1/live/projects/{projectId}`. `docs/protocol/cloud/live-channel.md` defines it.
  - **Access recheck:** the check that the API runs on each open live socket every 30 seconds. It reads the session and the member access of the reader again.
  - **`ProjectReader`:** the shared project access lookup in `crates/mkc-api/src/platform/project_access.rs`. It returns a project and the effective role of the reader.
  - **Workspace:** a team account. The store keeps the older name organization, so its rows are in `organizations` and its membership rows are in `memberships`.
- **Background:**
  - The "Access Checks" section of `docs/protocol/cloud/live-channel.md` makes the server check the session and the member access of each live socket every 30 seconds. A socket that lost access closes with code 4403.
  - `DatabaseSocketAccess` in `crates/mkc-api/src/live/access.rs` checks access at the upgrade, in `open` at line 51, and at each recheck, in `recheck` at line 72. Both call `member_role` (`crates/mkc-api/src/builds/reads.rs:20-28`), which calls `ProjectReader::read`.
  - REST reads use the same lookup: the build reads in `crates/mkc-api/src/builds/reads.rs`, the platform project reads at `crates/mkc-api/src/platform/policy.rs:45`, and the viewer reads at `crates/mkc-api/src/viewer/service.rs:35`.
  - `ProjectReader::read` reads the project. Then it calls `queries.members(project.organization_id)` and `queries.grants(id)`, and it keeps only the row of the reader from each list.
  - `members` (`crates/mkc-store-pg/src/member.rs:89`) loads every membership row of the workspace. `grants` (`crates/mkc-store-pg/src/grant.rs:82`) loads every grant row of the project.
  - The platform migration has the unique keys `(organization_id, user_id)` on `memberships` and `(project_id, user_id)` on `project_grants` (`crates/mkc-db/migrations/202609161100_platform/up.sql:36` and `:57`). So one indexed lookup can find each row of one reader.
  - `user_memberships` (`crates/mkc-store-pg/src/member.rs:101`) already reads the membership rows of one user. No store query reads the grant of one user on one project.
  - Access reads use the shared store pool of the API replica, which holds up to 8 connections. REST requests and build work use the same pool.
- **Problem:** Each access check loads the whole membership list of the workspace and the whole grant list of the project to find one reader. Suppose that each member of a workspace holds an open socket. Then each 30-second round reads a number of membership rows that grows with the square of the member count.
- **Impact if no action:** Passive viewers make repeated full-list reads. Those reads compete with REST requests and build work for the shared query pool of each replica.
- **Root question:** How can an access check for one reader cost the same in a large workspace as in a small one?
- **Options:**
  - **A.** Use indexed lookups for the two role rows of the reader at the socket upgrade and at each recheck. Keep the REST lookup as it is. Cost: sockets and REST then have two access lookups. Effort: Medium.
  - **B.** Give project access one shared lookup for the effective role of the current user. The lookup reads only the membership row and the grant row of that user. `ProjectReader` uses it, so REST and sockets both get it. Cost: a new store query for the grant of one user, and the project access tests that mock `members` and `grants` change. Effort: Medium.
  - **C.** Check the open sockets of a replica in groups, with one database query for each group. This reduces round trips, and it adds scheduling and result handling. Effort: Large.
  - **D.** Give every single-reader role check one lookup that reads only the rows of that reader. Add store queries for the workspace membership and the project grant of one reader, or use the existing `user_memberships` for the membership. Use the lookup in project access, in the workspace role checks of the platform, GitHub, and billing services, and in the catalogue policy of `mkc-publications`. Keep the list queries for listing pages, owner counts, and seat counts. Cost: 34 mock setups of `members` and `grants` in 14 unit test files change, and the catalogue server changes too. Effort: Medium.
  - **E.** Signal access changes from Postgres. Triggers on memberships, project grants, projects, and sessions notify the replicas, and each replica checks the affected sockets at once. The 30-second check then reads only the session row. Cost: a migration, a new relay channel, a check of every socket after a lost subscription, and a protocol change. Effort: Large.
- **Left out:** A cache of the full membership lists between checks adds a second source of access state, and it can delay a revocation. C is better on every point. A separate pool or a limit on concurrent rechecks fails the goal, and the database has no spare connections for another pool. A longer recheck interval, or closed sockets in hidden tabs, lowers the number of checks, not the cost of each check. The number of statements in one check is not a real choice.
- **Wider fix:** D. Every role check of one reader then reads only the rows of that reader. A new role check then has no full-list pattern to copy. The six workspace role checks at `crates/mkc-api/src/platform/policy.rs:20`, `crates/mkc-api/src/github/policy.rs:24`, `crates/mkc-api/src/billing/read.rs:22`, `crates/mkc-api/src/billing/checkout.rs:95` and `:144`, and `crates/mkc-api/src/billing/portal.rs:27` each load every member of the workspace to find one reader. The private-file policy of the catalogue server at `crates/mkc-publications/src/policy.rs:86-94` loads every member and every grant for each private file request.

- **Action:** fix after merge, apply B, because it changes shared authorization queries and their REST callers.
