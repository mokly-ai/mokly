# Vite base can render the wrong workspace export

- **Severity:** High. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-27, from finding 1 of round 1 of the review of branch `calummoore/storybook-d6-b-vite-workspace-sources-isfc`, at commit `168567607`, with the options of its finding check. The check of this item on the same day added the case of a build link in the working tree.
- **Location:** `ViteLookup.resolveWith`, which `ViteLookup.resolve` and `ViteLookup.resolveFromHook` call, and `ViteLookup.resolve` in `packages/mokly/src/sidecar/vite-resolution.ts`, at line 95 at commit `168567607`, and the same fallback loop in `resolveViteStylesheet` in `packages/mokly/src/sidecar/vite-stylesheet-lookup.ts`, `ViteLookup.nodeEntry`, and `ViteLookup.syncTarget` of that file, `ViteLookup.sync`, which `resolveConfigModule` in `packages/mokly/src/sidecar/vite-config-resolution.ts` calls for each bare import or require that Node resolves while the Vite config runs, `viteLookupImporters` in `packages/mokly/src/sidecar/vite-lookup-paths.ts`, `ModulePaths.resolve` and `ModulePaths.resolveSync` in `packages/mokly/src/sidecar/module-paths.ts`, at lines 242 and 276 at commit `168567607`, `bundleViteConfig` in `packages/mokly/src/sidecar/vite-config-bundle.ts`, `workspacePackage`, `workspaceTarget`, and `workspaceImport` in `packages/mokly/src/sidecar/workspace-imports.ts`, and the section "Workspace Package Sources" of `docs/protocol/mokly-comparison-packages.md`.
- **Reason:** The recommended fix applies the lookup recovery under the Vite adapter, which the protocol page excludes and no user decision allows, so it waits for the user.

- **Source:** Review.
- **Category:** Product bug.
- **Terms:**
  - **Vite adapter:** The compile path, turned on by `"vite": true`, in which the project's Vite setup selects each file, in place of the default esbuild path.
  - **Changes, head, and base:** Changes is Mokly's comparison of the head, the render of the working tree, with a base, the render of a Git commit.
  - **Working installation:** The `node_modules` folder of the working tree, whose links to workspace packages lead to the package folders of the head.
  - **Source rule:** The workspace package source rule, which loads a matching source file, such as `src/old.ts`, in place of a build file, such as `dist/old.js`.
  - **Lookup recovery:** On the esbuild path, when lookup fails, Mokly uses the one source file to which all targets of the matching `exports` key map.
- **Background:**
  - The section "Workspace Package Sources" of `docs/protocol/mokly-comparison-packages.md` states the source rule. It requires: "A link from the installation to a workspace package uses the manifest and files of the side being rendered."
  - A base uses the working installation when its dependency files equal those of the working tree. It also uses it as the fallback when its own install cannot run. The section "JavaScript Package Selection" of the same page and `docs/protocol/mokly-base-dependencies.md` give the fallback cases. Examples are an offline machine, the time limit, a missing lockfile, Bun, and an unsupported manager version.
  - A changed workspace `package.json` makes the dependency files differ. So a base with another export reaches the working installation only through the fallback. In a repository whose bases always fall back, such as a Bun repository, each branch that changes the export target of an imported workspace package meets the defect. Such a branch is still an unusual input, so the likelihood is Rare.
  - Under the Vite adapter, Mokly resolves a bare import of a base from three places, in this order:
    - the importer
    - the matching importer folder in the working installation
    - the package folder in each `node_modules` folder of the configuration ancestors and of the `moduleResolution.packageRoots` entries, in that installation
  - At each place, Vite selects the file, or Node does for an import of a CommonJS Vite config. Mokly skips a result of the importer that lies outside the base files. `ModulePaths.resolve` then maps the real path of a selected file in the head's package folder to the same path on the base. The source rule runs on that path. A run-time require of the Vite config takes the same order through `ViteLookup.sync` and `ModulePaths.resolveSync`.
  - Design call D9 of the Storybook support plan, `plans/storybook-support.md`, says that under the adapter the Vite setup alone selects each file. Mokly's `moduleResolution` aliases, conditions, main fields, extensions, and loaders do not apply there. The section "Replaced Settings" of `docs/protocol/mokly-vite-adapter.md` states the same rule.
  - The user's answer of 2026-11-27 changed the call: the source rule then applies to a build target that the setup or its config loader selects for a bare package specifier. The user's reason: the Vite path and the esbuild path stay as similar as possible. A build target that the setup cannot select still fails, such as a build file that Vite's own package lookup does not find in the working tree.
  - In the same answer, the user did not choose a full recovery that honors Vite's export conditions when lookup selects no file. The protocol section says: "The lookup recovery above does not apply under the adapter." Its decision rejects "a recovery when the setup selects no file, because it copies Vite's export rules."
  - The esbuild path fixed the same mismatch in pull request #596. `workspacePackage` in `packages/mokly/src/sidecar/workspace-imports.ts` compares the side's `package.json` with the copy that the installation reaches. When they differ, `resolveImport` in `packages/mokly/src/sidecar/importer-resolution.ts` repeats the lookup in the side's own package folder. When that lookup fails, the lookup recovery runs on the side's `package.json`. `retryRequire` in the same file does the same for a require that Node loads, with the `main` field.
  - A probe of Vite 8.3.8 looked up a base package that exports `./dist/old.js`. With the build, a self-reference lookup and a lookup of the package folder both selected `dist/old.js`. Without the build, the self-reference lookup gave no file, and the folder lookup gave the missing `dist/old.js`. For a package with only a `main` field, the self-reference lookup gives no file. Without the build, the folder lookup gives none either.
  - For Vite's own package lookup, a base with its own installed dependencies fails under the adapter for a Git-ignored build file, because its installation copies only tracked files. A probe of such a base gave `Failed to resolve entry for package "local"` under Vite, and esbuild compiled `src/old.ts`. The section "Workspace Package Sources" states this limit. Options A, C, and D act only when the two `package.json` files differ, so they do not change it.
  - A probe on 2026-11-27, with Node 24.21.0 and Vite 8.3.8, used a package `local` at `packages/local`. The base exported `./dist/old.js`. The head exported `./dist/new.js` and had `dist/new.js`. The base used the working installation. The results:
    - With base `src/old.ts` and `src/new.ts`, esbuild compiled the base `src/old.ts`, and Vite compiled the base `src/new.ts`.
    - With only base `src/old.ts`, esbuild compiled `src/old.ts`. Vite failed with `module packages/local/dist/new.js has no source in this side; set moduleResolution.sourcePackages for local`.
    - With a tracked base `dist/old.js`, a base `src/new.ts`, and no base `src/old.ts`, esbuild compiled the base `dist/old.js`, and Vite compiled the base `src/new.ts`.
    - With `import { value } from "local"` in the base `vite.config.mjs`, the page that shows the config value rendered `source base new` in place of `source base old`.
  - A second probe on the same day gave both sides the export `./esm/value.js`. The head linked `esm` to `release`. The base had a regular `esm/value.js` and used the working installation. Equal exports keep the dependency files equal, so this case needs no fallback. The results:
    - With a base `release/value.js`, esbuild compiled the base `esm/value.js`, and Vite compiled the base `release/value.js`.
    - Without a base `release/value.js`, esbuild compiled `esm/value.js`. Vite failed with `module packages/local/release/value.js has no source in this side; set moduleResolution.sourcePackages for local`.
  - `ViteLookup.resolve` gives `ModulePaths.resolve` no declared target, so Mokly maps the real path that Vite selected. On the esbuild path, `workspaceTarget` maps the export target whose real path equals the native file. Pull request #596 added it for the defect "The base followed the build link of the working tree". Options A, C, and D act only when the two `package.json` files differ, so they do not fix the link case. B and E fix it.
  - Design call of 2026-11-27, made when this item was written: for a package without `exports`, C and D read the targets of the main fields that the lookup uses. A Vite import uses the setup's `resolve.mainFields` and then `main`, because the setup takes the place of Mokly's main fields. A module that Node loads for the Vite config uses `main`, as `retryRequire` and `bundleViteConfig` do.
  - Each direct fix has these needs:
    - Put the fix inside `ViteLookup`. Each Vite lookup of Mokly goes through it: the plugins, the module runner, the stylesheet resolver, the config loader, the external check, and the React peers.
    - Record each `package.json` that the fix reads as a lookup input. Then a rebuild in Serve, the development server, after an edit of that file compiles the same files as a fresh build.
    - Where Node selects the file, repeat the lookup in Node from the side's package folder, as `retryRequire` does. This covers a bare import of a CommonJS Vite config and each run-time import or require of the Vite config. Both reach `ViteLookup.syncTarget`, so put the Node form there.
    - In `resolveViteStylesheet` in `packages/mokly/src/sidecar/vite-stylesheet-lookup.ts`, keep the check for a relative file ahead of the package lookup, so that the fix sees only package imports.
    - The `workspace` helper in `tests/fixtures/vite_workspace.ts` builds a base on the working installation, with `dependencyRoot: head`, and writes one `exports` value for both sides. `tests/sidecar_vite_workspace_sources.test.ts` uses it. Give the two sides different exports there. Test with both build files present and with no base build.
- **Problem:** Through the working installation, Vite selects a file of the head's package, and Mokly maps the real path of that file to the base. So a base that exports `dist/old.js` can load `src/new.ts`, the source of the head's export, also when the base tracks `dist/old.js`. With equal exports, a link in the head from `esm` to `release` makes the base load `release/value.js` in place of its own `esm/value.js`.
- **Screenshot:** None, because the review and its finding check are read-only and ran sidecar probes, not a Changes run. In Changes, a base preview whose two exports give different labels would show the label of the head's export.
- **Impact if no action:** Changes can compare the head with the output of the wrong base file, so it can show a change that the branch did not make, or hide one. When the base lacks the file that the head's selection maps to, the base render fails with a message that names the head's path. The export-condition route does not help such a base: with a `development` target in each manifest, the base still compiles the head's source, because Vite reads the head's manifest.
- **Root question:** How does each side use its own workspace export when it shares the working installation?
- **Options:**
  - **A.** Reuse the manifest check of pull request #596 on the Vite path. When the side's `package.json` differs from the copy that the installation reaches, ask Vite to select an existing file from the side's own package folder. Test the fallback with both build files present. Cost: a side that lacks its build has no file for Vite to select, so A does not fix that case. That is the usual case for a build that Git ignores. Effort: Medium.
  - **B.** Build option C of [workspace-import-resolution-record.md](./workspace-import-resolution-record.md), with its Vite part. That record holds the selected package scope, the import form, and the declared target before the source rule, on every compile path. It reaches the JavaScript, CSS, and Node lookups. It still needs the rule of C or D for a side with no file to select. Effort: Large.
  - **C.** Do A. When the side's package has no file that Vite can select, compare the targets that the matching `exports` key names in the two `package.json` files. When they are equal, keep the head's selection, mapped to the side. When they differ, fail with a message that names the package and the two routes: an export condition such as `development`, or an alias in the Vite setup. Cost: C adds a new build error, which only the user can approve. The section "Workspace Package Sources" then needs the failure text. Effort: Medium.
  - **D.** Do C, but in place of its failure, apply the lookup recovery to the side's own `package.json`. The side then loads the one source file to which all targets of its matching key map. When the recovery finds no single source file, the import fails, as on the esbuild path. Cost: D changes design call D9 and the four passages of protocol text below. D also adds a build error where the recovery finds no single source file, a case that the current code can render with the head's export. Effort: Medium.
    - The sentence of the section "Workspace Package Sources" that excludes the lookup recovery under the adapter.
    - The decision of that section that the rule applies to the file that the setup selects.
    - The rejected recovery of that decision.
    - The Vite paragraph of the section "Source And Dependency Files" of `docs/protocol/mokly-sidecar-modules.md`.
  - **F.** Do D, and map the declared export target whose real path equals the file that Vite selected, as `workspaceTarget` does on the esbuild path. Pass that target to the source step as the declared package target. This also fixes the link case: the base then loads its own `esm/value.js`. Cost: the same as D, plus the target mapping on the Vite path. Run the target mapping on each Vite lookup, on both sides, so that the head link case also maps to the declared target. Send the retry through the `dispatch` that `ViteLookup.resolveWith` gets, so that a lookup inside a hook keeps Vite's request options. Read each `package.json` through `WorkspaceLookups.manifest`, so that config imports keep their setup evidence. Effort: Medium.
  - **E.** Give a base that falls back to the working installation its own dependency view, with links to the side's own workspace package folders. Vite then reads the side's own `package.json` and files. Cost: E fixes only which package the side reads. A side package without its build then fails with `Failed to resolve entry for package`, as a base with its own installed dependencies does. E also adds setup and cleanup to each such base, and it changes the fallback rule of `docs/protocol/mokly-base-dependencies.md`. Effort: Large.
  - **G.** Map the export branch, not the file, on each Vite lookup of a workspace package, on both sides. Find the export key and the condition branch, in the `package.json` that Vite read, whose target has Vite's real path. Take the target of the same branch in the side's own `package.json`, and pass it to the source rule as the declared target. When the side has no such branch, or the branch is not unique, do A, and when A gives no file, fail as C does. Cost: it honors the conditions that Vite applied without a condition walk, but only the Vite path has this rule, against the user's reason for answer B to track D decision 6. It needs a branch-aware form of `packageMapTargets`, the protocol and D9 changes of D, and the build error of C. Effort: Large.
- **Left out:**
  - A walk of the export conditions in Mokly. It copies Vite's lookup rules, and on 2026-11-27 the user did not choose the full recovery that honors Vite's export conditions.
  - A guard that fails the base on each difference between the two `package.json` files. It fails a base whose import is right, such as a base whose `package.json` differs only in its version.
  - A, with a base build from the base prepare command. That command is the setting `review.basePrepare`, which Mokly runs in a private copy of the base before the base render. The plan `plans/base-prepare-command.md` on branch `calummoore/mokly-base-prepare-command-7jlm` proposes it. It fails the goal for each base without that command. On 2026-11-27 the user also kept the base build in that plan.
  - A note in the docs only. It fails the goal, because the base still renders the wrong export with no message.
- **Wider fix:** B. One record gives each Vite lookup the side's package scope, the declared target, and the import form, so no consumer maps a file of the other side's package or reads a relative import as a package name.
