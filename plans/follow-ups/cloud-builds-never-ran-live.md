# Live cloud build proof is not recorded

- **Severity:** High (estimate). **Effort:** Small (estimate). **Confidence:** Medium. **Harder later:** No.
- **Kind:** Post-merge task.
- **Added:** 2026-10-30, from the post-merge notes of the deleted `plans/cloud-builds.md`, on the branch `calummoore/plans-skill-update`.
- **Location:** `docs/ops/build-template.md`, section "Live Evidence", and `infra/e2b/build/`.
- **Reason:** The proof needs an E2B account, a published template and the installed App, which no repository check uses.
- **Checked:** 2026-11-24. The template `mokly-build-v2` (build reference `f1x5cj2fgwv20p42qxnn:2f7ad3b2-ffae-4e31-a4e9-33f3d2d26374`) passed the live probe, and the "Live Evidence" section of `docs/ops/build-template.md` records it. The API deployments of main-preview and production had no build settings, so builds were off in both. The main-preview Secret Manager secret `mkc-main-preview-e2b-api-key` had one enabled version. The production secret had no version. The agent token could not read or write the GitHub Actions variables, because GitHub answered HTTP 403.

- **Terms:**
  - **E2B:** The sandbox provider that runs each cloud build attempt in a one-shot sandbox.
  - **Build template:** The E2B template `mokly-build-v<N>` that `infra/e2b/build/` defines and `docs/ops/build-template.md` releases. The release in use is the build reference in the `builds.template` value of the environment's app-config. On 2026-11-26, main-preview moved to `mokly-build-v5`, build reference `tpjwc7qiz8bp7bvnpzp7:433b3d4d-1e81-4d54-8963-d62eceb3ecc8`, whose Git 2.56.1 can read a comparison base. Later that day it moved to `mokly-build-v6`, build reference `mm5vcm4xv7inkey7ad9p:e58c1440-c5e2-406d-97a3-8d312416c61c` through Deploy run 45818241716. v6 keeps Git 2.56.1, adds PCRE2 to it, and keeps the base image's C and C++ toolchain. v5 is superseded, because it has no C and C++ toolchain and its Git has no PCRE2. `mokly-build-v7`, build reference `ez8gf58grc5zofiqv7ql:548d54fd-072d-47eb-b484-e90e23471ecb`, is the release on plain Debian 13. Its Git 2.47.3 can also read a comparison base. Cal switches main-preview to v7 after the v7 Dockerfile merges into `main`. The current probe fails on v5 and v6. Both hold a second Python and a second Git. `mokly-build-v3` cannot compare, because its Git 2.39.5 rejects `git cat-file --batch --filters -Z`. `mokly-build-v2` is not a release, because its npm is broken.
- **Background:** The list below gives the facts.
  - PR #45 added cloud builds on 2026-10-20. The worker runs the repository's own `mokly publish` in a sandbox and posts build checks.
  - Every repository check runs without E2B.
  - On 2026-10-30, `docs/ops/build-template.md` said that no E2B candidate had been published or verified, and that no cloud resource or key had been provisioned.
  - The repository cannot show whether a resource, a key or a live build exists outside it.
  - Builds default to off, and PR previews cannot enable them. The preview seed of PR #81 starts no background worker, so a preview seed proves no sandbox build.
- **Task:** Prove cloud builds live, first on `main-preview`, then on production.
  - First choose the newest release in "Live Evidence" of `docs/ops/build-template.md` whose record does not rule it out. A record rules a release out when it says that it is not a release, or not to deploy it or roll back to it. On 2026-11-26 that is `mokly-build-v7`, build reference above. Its record holds a pass of the current probe at 2026-11-26T15:41:58Z. Probe the chosen release with the current assertion, as "Verify The Streaming Boundary" says for a published release. Record the pass, the commit of the assertion, and the UTC time in that release's record. Rotate or enable `main-preview` builds only after that pass.

    On 2026-11-26, `builds.template` in `MKC_MAIN_PREVIEW_APP_CONFIG` held the v6 reference above. The recorded v6 pass ran the probe from `main` at `1ce3ed0be`. That probe requires Git 2.43 or newer and runs `git cat-file --batch --filters -Z`. Its UTC time is not recorded. On v6, the smoke repository's pull request build at `c11aa3fe8` published at 12:46:31 UTC. Its check said "Catalogue ready to review." and reported two changes.

  - When `main-preview` already runs the probed reference, change nothing. When it runs another reference, change only the build reference and keep the deployment ID, as "Rotate, Roll Back And Disable" says. When builds are off, add the `builds` group to the `MKC_MAIN_PREVIEW_APP_CONFIG` GitHub variable, as "Provision And Enable One Environment" says. Then deploy. The proof below runs on that deployed reference.
  - When the probe or a build on that reference fails, roll back only as the runbook's rollback rule says, or disable `main-preview` builds. Do not restore `mokly-build-v3`, because it cannot compare, or `mokly-build-v2`, because its npm is broken. A rollback to `mokly-build-v5` breaks each install that compiles a native addon.
  - With the `mokly-main-preview` App installed on the test repository `mokly-ai/mokly-build-smoke` (created 2026-11-25) and its main-preview project created, push to its default branch and open a pull request. Push a new commit to the pull request after the rollout completes.
  - Watch the check of the build that this push started move from queued to a Changes result. The build must have published its own catalogue: the publication of its `publicationId` has a `buildId` equal to the build ID, and the build log's result line starts with "Published Mokly catalogue.". A ready publication from another producer, such as a CI upload of the same head, can stand in for the build, and its check then shows that upload's comparison. On such a mismatch, push another commit. Then press Re-run, which proves only the re-delivery of the stored result.
  - Record the result in the "Live Evidence" section of `docs/ops/build-template.md`.
  - Repeat the proof on production after promotion. First add a version to `mkc-production-e2b-api-key` and set `MKC_PRODUCTION_APP_CONFIG` with its own deployment ID. Record the timings of a cold install against the 15-minute budget.
- **Impact if no action:** No stable deployment has a passing cloud build, so users cannot use the product's default onboarding path.
- **Needs:** The effort counts code changes only. The operator work of provisioning and the live runs has no sized patch. An E2B team key, the template release, a GitHub test repository with the App installed, and access to both stable environments.
- **Done when:** The "Live Evidence" section records a successful build, check and Re-run on both environments. Each record gives the released template ID, its source revision, the environment, the publication receipts, the check URLs and the cold-install timings.
