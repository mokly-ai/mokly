# Receiver index checks are narrower than the viewer's

- **Severity:** Medium. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-02, from Decision 9 of the Mokly 0.18.0 upgrade on the branch `calummoore/mokly-cli-upgrade`. The Milestone 1 docs agent raised it on 2026-11-01, and an options check added option E.
- **Location:** `docs/protocol/publication-review.md`, section "Fields The Receiver Reads", and `crates/mkc-mokly-contract/src/index_validation.rs`.
- **Reason:** On 2026-11-02 the user deferred the choice, so the receiver keeps the narrower checks that the docs describe until the user decides.
- **Category:** Docs or spec.

- **Terms:**
  - **Catalogue index:** `mokly-viewer/index.json`, the file that lists each screen of a 0.18.0 catalogue and its Changes. The Plan request of an upload carries it.
  - **`readCatalogueIndex`:** the public reader in `@mokly/viewer` that checks a whole catalogue index.
- **Background:**
  - Since 2026-10-10, a requirement said that the cloud never accepts an upload that the viewer refuses.
  - For 0.14.0, the receiver had a 1,700-line Rust copy of the viewer's review reader, which still accepted reviews that the viewer refused.
  - Mokly 0.17 removed the review file. The receiver now checks only the index fields that it reads: the base fields, the record paths and titles, `changes`, and the screen view axes. It ignores other fields.
  - A corpus test proves that the Rust reader and `readCatalogueIndex` give equal Changes counts.
  - The app checks the whole index with `readCatalogueIndex` before it shows the viewer.
- **Problem:** The receiver can accept an index that the pinned viewer refuses, for example one with a malformed tree.
- **Impact if no action:** A broken index from a faulty producer is published. The app shows its failed-index card "This publication couldn't open", whose **Try again** can never succeed. The GitHub check can show counts for a catalogue that never opens.
- **Root question:** What does the cloud promise for an upload whose index the pinned viewer refuses?
- **Options:**
  - **A.** Keep the docs as written: the receiver checks only the fields that it reads. The harm stays in the uploader's own project, because an upload needs that project's token. Effort: Small.
  - **B.** Also check selected structural rules that affect the app, such as tree membership. Effort: Medium.
  - **C.** Check the whole index in Rust, as `readCatalogueIndex` does. This second reader can drift at each release, as the review reader did. Effort: Large.
  - **D.** Run the published `readCatalogueIndex` in a Node process at upload time. The receiver then agrees with the viewer on every rule, but the API gets a Node runtime. Effort: Large.
  - **E.** Ask Mokly to publish its index rules as a Rust crate, and run it at the exact pin. This waits for a release, and it needs A or B until then. Effort: Large.
- **Left out:** None.
- **Wider fix:** D, because it runs the viewer's own reader after each pin bump. E gives the same result without Node, but only after a Mokly release.
- **Previous examples:** `plans/follow-ups/review-reader-accepts-viewer-refused-reviews.md`, deleted with the review reader in the 0.18.0 upgrade.
- **Recommendation:** A. The harm stays in the uploader's project, and the fields that the check and the screens list use stay checked. D protects the code best.
- **Action:** ask the user, because A drops the requirement of 2026-10-10 that the cloud never accepts more than the viewer.
