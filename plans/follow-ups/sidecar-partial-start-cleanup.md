# Verify cleanup after partial sidecar startup

- **Severity:** High. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Post-merge task.
- **Added:** 2026-11-18, from the factory ownership trace of the sidecar memory guard repair.
- **Location:** `crates/mokly-sidecar/src/process_factory.rs`, `crates/mokly-sidecar/src/process_reaper.rs`, and `crates/mokly-platform/src/unix_process_tree/group.rs`.
- **Reason:** The memory guard preserves existing startup cleanup. Proving whole-tree cleanup after partial setup needs a separate lifecycle task.

- **Terms:**
  - **Factory:** The boundary that creates the Node sidecar and returns its worker and process control.
  - **Process group:** The platform guard that owns the sidecar and its descendants.
  - **Reap:** Wait for a child to exit and collect its status.
- **Background:**
  - `NodeFactory` can fail after child creation while attaching the process group or starting pipe threads.
  - On Unix, attachment reads the child's process identity before it creates the group guard. That read can fail.
  - `Reaper::reap` calls the direct child's kill and wait methods. It discards both results after recording startup timing.
  - An attachment failure therefore has no group guard. Direct-child cleanup does not establish what happens to descendants that already exist.
  - A pipe-thread failure calls `control.kill()`. That call can fail, and the returned startup error carries no successful whole-tree cleanup proof.
  - The memory guard's `SpawnFailure::Started` retains the slot's memory reservation after these failures. It makes no claim that the process tree ended.
  - `crates/mokly-sidecar/tests/startup_timing_tests.rs` covers a real child and failed attachment. Its stop-span assertions do not establish descendant cleanup.
  - Nobody reproduced a surviving descendant in this trace. The concern comes from the ownership and error paths.
- **Task:**
  - Exercise attachment and partial pipe-thread failures with a sidecar that has a descendant.
  - Use the existing injected platform boundaries to control the failures.
  - Record the direct-child and descendant cleanup results, including kill or wait failures.
  - Check the existing lifecycle requirement that a sidecar does not outlive its binary.
  - If the trace confirms a defect, propose its repair under the decision and review rules.
- **Impact if no action:** A partial startup failure can leave the core without proof that its created process tree ended.
- **Needs:** The existing process fixtures, platform mocks, and process-ownership checks. No new infrastructure is required.
- **Done when:** The cleanup result is established for both failure stages. Each confirmed defect has a reviewed fix or a decision item.
