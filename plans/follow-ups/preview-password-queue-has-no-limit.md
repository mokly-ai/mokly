# Preview password queue has no limit

- **Severity:** High. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-26, from the branch `calummoore/preview-password-sign-in-jofl`, round 2 review, finding 9, "Preview password wait has no capacity limit". Options D, E and F come from its finding check. It is a security finding that waits for the user, so it holds the pull request of that branch until the user answers.

- **Source:** Review.
- **Category:** Security.
- **Terms:**
  - **PR preview:** a temporary Mokly Cloud deployment for one labelled pull request. Only previews configure the password exchange.
  - **Admission:** the API's persistent count of attempts per key in a 60-second window, kept in the database. A full window answers 429 `rate-limited`.
  - **Check slot:** one of the two permits of `PreviewHashSlots`. A password check runs only while it holds one.
  - **Overload refusal:** an immediate error answer that a full capacity limit gives in place of a wait.
- **Background:**
  - `POST /v1/auth/preview` signs a reader in to the shared account of a PR preview with the preview password. Production has no shared account, so it answers 503 `operation-unavailable`.
  - The router runs the first phase of every JSON request on a blocking worker. `dispatch_request` in `crates/mkc-api/src/router.rs:224-233` does this.
  - For this exchange, `admit_preview` checks the password length and then commits admission through `AuthService::preview_sign_in`. Admission allows 20 attempts per selected client IP per 60 seconds, under the key `preview:{peer}`.
  - `AdmittedPreview::finish` then waits for a check slot with `acquire_owned().await`, without a worker. Only an attempt that holds a slot runs scrypt on a blocking worker.
  - The semaphore has no limit on waiters. Each admitted attempt keeps its connection, its request and its password in memory until it gets a slot.
  - Two checks run at a time, so the last of N waiting attempts waits about N/2 check durations. The operator command makes verifiers with `ln=14,r=8,p=5`, in `infra/scripts/preview-lifecycle.py:90-93`.
  - A PR preview runs one API process, as `infra/helm/mokly-cloud/environments/preview-pr.yaml:11-13` and `infra/helm/mokly-cloud/templates/workloads.yaml:10-12` set.
  - Preview API requests pass Cloudflare and then ingress-nginx, as `docs/protocol/cloud/pr-preview-environments.md:46` says. By default, Cloudflare ends a proxied request that has no answer after 100 seconds. Terraform sets no other value. ingress-nginx waits 300 seconds, in `infra/helm/mokly-cloud/templates/ingress.yaml:9`.
  - Any client can send attempts without the password. A client with many addresses, such as an IPv6 /64, gets a fresh admission window for each address.
  - Before the branch `calummoore/preview-password-sign-in-jofl`, the exchange compared one SHA-256 hash, so no attempt waited. That branch added the scrypt verifier and the two check slots.
  - The section "Password Exchange" of `docs/protocol/cloud/preview-sign-in.md:141-143` says: "One API process checks at most two passwords at once, and further attempts wait, so the memory of concurrent checks stays far below the API's limit."
  - That branch recorded this rule as its own design call, not as a user decision. Its reason was that each check uses about 16 MiB and the API's memory limit is 1 GiB.
  - Sign in shows each refusal of the password section beside its action, except `magic-link-invalid`, and the action then reads Try again. The app's sentence for `unavailable` is "Mokly is busy. Try again in a moment.", in `packages/app/src/api/form-error.ts:35`.
- **Problem:** The two check slots bound the checks that run, not the attempts that wait for them. Admission bounds each client address, not the sum over all addresses. So the queue, its memory and its waiting time grow with the number of addresses that send attempts.
- **Impact if no action:** Traffic above the check rate makes valid attempts wait past the 100-second deadline of Cloudflare. Readers with the right password then cannot sign in to the preview. The queue also takes more memory as it grows.
- **Root question:** How can a preview answer every password attempt within the proxy's deadline, with bounded memory, however many addresses send attempts?
- **Options:**
  - **A.** Accept an attempt only when a check can start. Take a check slot without waiting, and answer 503 `unavailable` at once while both slots are busy. This also refuses an ordinary burst, such as a third reader who presses Continue while two checks run. Effort: Small.
  - **B.** Give the exchange one capacity limit for its waiting and running attempts in each API process. After the Origin and body checks, take a place without waiting, before the admission transaction. Take it with `try_acquire_owned`, as the upload admission does in `crates/mkc-api/src/upload_plan.rs:125-130`. When no place is free, answer 503 `unavailable` at once. Such an attempt consumes no admission and writes nothing. An attempt with a place still passes the per-IP admission. Release the place when the attempt ends or its request is dropped. Choose a limit that leaves room for a short burst of normal use. The app already shows `unavailable` beside the action, so the app needs no change and the API needs no new reason. In the section "Password Exchange" of `docs/protocol/cloud/preview-sign-in.md`, add the capacity step to the check order at lines 126-127. Change the admission sentence at lines 133-134, because a refused attempt consumes no admission. Replace "further attempts wait" at lines 141-143 with the limit and its refusal. Widen the "When returned" text of the `unavailable` row in `docs/protocol/cloud/rest-api.md:76`, which says "Explicitly retryable dependency outage". Test with event order: hold both check slots, fill the limit, and assert that the next attempt answers 503 `unavailable` while health still answers. Bound the waits of the test with an expected-state timeout, as `crates/mkc-api/src/_tests_/preview_queue_tests.rs` does. Effort: Medium.
  - **C.** Run preview password checks in their own executor, with a capacity limit and fair scheduling across groups of client addresses. It also isolates the CPU work of scrypt, and it adds a worker lifecycle to maintain. Effort: Large.
  - **D.** Declare limits for every operation in one table. Each row limits waiting requests and running requests, and gives the same overload refusal beyond them. The password exchange becomes one row of that table. `plans/follow-ups/api-operations-share-one-blocking-pool.md` holds this work as its option B. Effort: Large.
  - **E.** B, and a deadline of 10 seconds on the wait for a check slot. An attempt that waits longer answers 503 `unavailable`. It bounds the wait of each attempt as well as the number of attempts, and it adds a timer and a second refusal path. Effort: Medium.
  - **F.** B, and an in-memory digest of the accepted password, keyed with a random secret of the process. An attempt whose password matches the digest skips the wait and scrypt. A reader with the right password then never waits behind wrong attempts. The first right attempt after a start still waits. It keeps a fast check of the password in memory, so it needs a security review. Effort: Medium.
- **Left out:**
  - Change nothing. The queue stays without a bound, so it fails the goal.
  - More check slots or a larger blocking pool. They raise the work that the API holds, and the queue can still grow without a bound.
  - Count IPv6 addresses by their /64 prefix in admission. It improves one admission key, and the total over all clients stays open. `plans/follow-ups/auth-admission-keys-full-ipv6-address.md` holds that work.
  - B with 429 `rate-limited` and `Retry-After: 1`, as option A of `plans/follow-ups/api-operations-share-one-blocking-pool.md` sketches. A 429 tells one client that it sent too many requests, but the overload comes from all clients together. The OpenAPI document also describes the 429 of this operation as "Persistent peer admission limit reached."
- **Wider fix:** D. One table bounds the waiting and running requests of every operation, so no operation can queue without a bound.
- **Previous examples:**
  - The upload admission of the same API takes one of two places with `try_acquire_owned`, and answers 503 `upload-unavailable` when none is free. See `crates/mkc-api/src/upload_plan.rs:125-130` and `crates/mkc-api/src/publishing.rs:117`.
  - `plans/follow-ups/bundle-cache-request-cost.md` weighs a bound on pending work in the render service.
  - Until 2026-11-25 each admitted password attempt also held a blocking worker while it waited. The branch moved the wait off the pool, and the queue stayed open.
- **Related:** `plans/follow-ups/api-operations-share-one-blocking-pool.md`, a shared wider fix. Its option B is option D here. Its option A caps the same password queue, so the answer here also settles that option. Its option B should reuse the refusal that the answer here chooses.
- **Recommendation:** B. It bounds the work that one API process accepts from all client addresses, and it leaves room for a short burst. It uses a reason and a sentence that the app already has. D best protects the codebase, because one table then bounds every operation.
- **Action:** ask the user, because B adds an overload refusal and changes the requirement "further attempts wait" in `docs/protocol/cloud/preview-sign-in.md`. No recorded user decision covers either change.
