# A stylesheet request changes Vite config values

- **Severity:** High. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-27, from the check of finding 9 of round 2 of the review of branch `calummoore/storybook-d6-b-vite-workspace-sources-isfc`, at commit `9ce7cfc86`. The findings file of that review lists it as item 11. Options A and D here are options D and C of finding 9. Options B and C are new.
- **Location:** `ViteCompiler.stylesheet` in `packages/mokly/src/sidecar/vite-compiler.ts:150`, `ViteStylesheets::new` in `crates/mokly-render/src/vite_stylesheets.rs:47`, `stylesheets::attempt` in `crates/mokly-render/src/stylesheets.rs:43`, `ViteContext.open` in `packages/mokly/src/sidecar/vite-context.ts`, at lines 81 and 130 at commit `9ce7cfc86`, `ViteLookup.updatePaths` in `packages/mokly/src/sidecar/vite-resolution.ts:50` at commit `9ce7cfc86`, `withViteConfigResolution` in `packages/mokly/src/sidecar/vite-config-resolution.ts:32`, `ModulePaths.workspaceSource` in `packages/mokly/src/sidecar/module-paths.ts:187` at commit `9ce7cfc86`, `bundleViteConfig` in `packages/mokly/src/sidecar/vite-config-bundle.ts:117`, the section "Workspace Package Sources" of `docs/protocol/mokly-comparison-packages.md`, and the `transformViteCss` row of the method table in `docs/protocol/mokly-sidecar.md`.
- **Reason:** Every option changes a requirement in force that no recorded user decision covers: the exact-path rule for imports of the Vite config, or the empty lists of the `transformViteCss` call.

- **Source:** Review.
- **Category:** Product bug.
- **Terms:**
  - **Vite adapter:** The compile path, turned on by the `vite` field of `mokly.config.json`, in which the project's Vite setup selects and transforms each file.
  - **Setup:** The Vite config and its plugins, which one sidecar process loads at its first Vite request and reuses for its later requests.
  - **Bundle request and stylesheet request:** The sidecar calls `bundle`, which compiles the JavaScript entries of a side, and `transformViteCss`, which transforms one stylesheet through the setup.
  - **Configured file:** A file that the sidecar keeps at its exact path under the source rule: an entry module, a stories file, the renderer, or the Storybook preview.
  - **Source rule:** The workspace package source rule, which loads a matching source file, such as `src/value.ts`, in place of a build file, such as `dist/value.js`.
- **Background:**
  - The section "Workspace Package Sources" of `docs/protocol/mokly-comparison-packages.md` states the source rule. Under the Vite adapter, the rule applies to each file that the setup selects for a bare package specifier. It also applies to each file that Mokly's bundle of the Vite config file selects. The user chose this on 2026-11-27, so that the Vite path and the esbuild path stay as similar as possible.
  - The same section requires: "A configured file keeps its exact path, including when a package import reaches it." So a config import of a configured build file loads that build file, not its source. The section also counts the local stylesheets that the configuration names. Its status line says that the code does not keep them exact yet, and [configured-stylesheet-package-imports.md](./configured-stylesheet-package-imports.md) covers them.
  - Each sidecar process runs one Vite server for its source root, under the section "The Vite Server" of `docs/protocol/mokly-vite-adapter.md`. The process loads the setup at its first Vite request. Its later bundle and stylesheet requests reuse the setup and the values of its config, such as `define` values and plugin options.
  - `bundleViteConfig` in `packages/mokly/src/sidecar/vite-config-bundle.ts` selects the file of each config import through the module paths of the request that loads the setup. `ModulePaths.workspaceSource` in `packages/mokly/src/sidecar/module-paths.ts` skips the source rule for a configured file of those module paths.
  - The setup keeps one `ViteLookup` for its requests. Each later request calls `ViteLookup.updatePaths` in `packages/mokly/src/sidecar/vite-resolution.ts`, which puts the module paths of that request into the shared lookup. `withViteConfigResolution` in `packages/mokly/src/sidecar/vite-config-resolution.ts` gives that lookup to each module that Node loads for the config during the request.
  - A bundle request lists the entry modules, the stories files, and the renderer. `entryModule` in `packages/mokly/src/sidecar/bundle-entry.ts` finds the Storybook preview when stories files exist, and `ViteCompiler.bundle` in `packages/mokly/src/sidecar/vite-compiler.ts` adds it to the configured files. A stylesheet request lists only the renderer:
    - The method table of `docs/protocol/mokly-sidecar.md` gives the `transformViteCss` call "the side's `bundle` settings with empty entry and stories file lists".
    - The doc comment of `TransformViteCss.setup` in `crates/mokly-sidecar/src/vite_css.rs` says "without JavaScript entries", and the generated `packages/mokly/src/generated/sidecar/TransformViteCssParams.ts` copies it.
    - `ViteStylesheets::new` in `crates/mokly-render/src/vite_stylesheets.rs` builds these lists with `bundle_inputs::params(config, &[], side)`, and its `stylesheet` method sends them.
    - `stylesheets::attempt` in `crates/mokly-render/src/stylesheets.rs` creates `ViteStylesheets` with no catalogue files. `bundle.rs` calls it once, and `graph.rs` calls it twice.
  - The core keeps a pool of sidecar processes for each side, and it sends each call to one of them. A head call is a call for the working tree, and a base call is a call for a Git commit. A stylesheet request is the first request of a process in these cases:
    - The pool sends a head `transformViteCss` call to a process without a compile while the process of the last compile is busy. `docs/protocol/mokly-sidecar-head-bundle-affinity.md` gives this rule.
    - The pool ranks only head processes by their last compile, at `crates/mokly-sidecar/src/pool_requests.rs:151`. So a base `transformViteCss` call takes an idle base process in queue order, also one that has no setup yet.
    - The pool replaces a process after a crash, or after a `fresh-worker-required` answer, which the sidecar gives when it must load the setup again. The pool then sends the same call to the new process.
    - In a catalogue without JavaScript, a stylesheet request opens the setup first, under a design call of 2026-11-18. Such a catalogue has no entry modules or stories files, so this case gives no other config values.
  - On 2026-11-27, the branch that found this item put the renderer in the setup key of `ViteContext.open` in `packages/mokly/src/sidecar/vite-context.ts`. The key still leaves out the entry and stories lists. So a reused setup also keeps the decisions of its first request when a later bundle request lists other entry modules. A read of the code shows this second case, and nobody ran it.
  - Under the adapter, the setup takes the place of the `postcss` module, under the section "Replaced Settings" of `docs/protocol/mokly-vite-adapter.md`. On the esbuild path, the `prepareContext` and `processCss` calls of that PostCSS config carry no entry modules, stories files, or renderer. So there the imports of the PostCSS config count no configured file of the catalogue.
  - A probe of the review, on 2026-11-27 at commit `9ce7cfc86`, called a sidecar process directly. It used a copy of the Vite fixture `tests/fixtures/vite`:
    - A package `local` at `packages/local`, linked from `node_modules/local`, exported `./dist/value.js`.
    - `dist/value.js` exported the value `"red"`, and `src/value.ts` exported `"teal"`.
    - `vite.config.mjs` imported `value` from `local` and set `define: { __VALUE__: JSON.stringify(value) }`. The page `src/workspace.mockup.ts` rendered `__VALUE__`.
    - The bundle request listed the page and `packages/local/dist/value.js` as entry modules. It set `renderer: null`, `sourcePackages: []`, so that the detected layout maps `dist` to `src`, and `packageRoots` with the fixture root and the Mokly repository root, so that `@mokly/mokly` resolves.
    - The stylesheet request sent the same settings with empty entry and stories lists, for `src/screen.css`.
  - A config import seldom reaches an entry module, a stories file, or the preview below a build folder, so the likelihood is Rare.
- **Problem:** A config import keeps the exact path of a configured file only when the first request of the process lists that file. In the probe, a bundle request as the first request rendered `red`, the value of the configured build file. A stylesheet request as the first request made the same bundle request render `teal`, the value of the source.
- **Screenshot:** None, because the review ran sidecar probes, not a browser. In Serve, the development server of Mokly, the page that shows the config value would show `teal` in place of `red`.
- **Impact if no action:** A fresh build and a Serve rebuild can render different config values from the same files. A comparison of two sides can then show a change that no file made, or hide one.
- **Root question:** How does the Vite config give each request the values that a fresh process gives it, whichever request loaded the setup?
- **Options:**
  - **A.** Load the Vite config with no configured files. Build the module paths of the config bundle, and of each module that Node loads for the config, from the request settings without the configured files. These settings are the source root, the configuration directory, the repository roots, and the module resolution settings. Keep these module paths apart from the swap in `ViteLookup.updatePaths`. The config then selects the same files for every request, and no later list can make its values stale. Keep the lookup evidence of these module paths in the evidence of the setup. Cost: a config import of a configured build file then loads its source, while the catalogue keeps the configured file. A changes the exact-path sentence of the section "Workspace Package Sources" for config imports. The test "Vite recompiles config and catalogue imports when a build becomes the renderer" in `tests/sidecar_vite_workspace_setup.test.ts` then expects the source value from the config. Effort: Medium.
  - **B.** Load the Vite config with the renderer as its only configured file. The entry modules, the stories files, and the Storybook preview then keep no exact path for a config import. Both calls carry the renderer, and the setup key holds it, so the config gives one result for every request. Cost: B changes the same sentence as A, with a narrower exception. A later setting that names a file must enter both calls and the setup key before the file can count for the config. Effort: Medium.
  - **C.** Give both calls the same configured files. A reused setup loads again when a change of these lists changes the exact-path decision of a config import. Effort: Large. The work:
    - Pass the catalogue files of the side to `stylesheets::attempt` at its three call sites, so that `ViteStylesheets::new` sends the entry and stories lists, as `bundle` does.
    - Run the preview check of `entryModule` for a stylesheet call too, and add the preview to its configured files.
    - Change the `transformViteCss` row of `docs/protocol/mokly-sidecar.md`, the doc comment of `TransformViteCss.setup`, and the generated `TransformViteCssParams.ts`.
    - Cost: a setup key on the lists is the simple form, but each entry module that Serve adds or removes then loads the setup again.
  - **D.** Build option C of [workspace-import-resolution-record.md](./workspace-import-resolution-record.md), with the configured files of C in both calls. Each workspace import record then holds its exact-path decision before the source rule, on every compile path. Setup reuse and the module graph compare these decisions, and they invalidate what a changed decision reaches, also each catalogue module. Cost: D has the request change of C, and it waits for the shared record, a Large change of every compile path. Effort: Large.
- **Left out:**
  - Change nothing. It fails the goal, because a fresh build and a Serve rebuild can render different values from the same files.
  - The entry and stories lists in the setup key, with no change to the calls. A stylesheet call has empty lists, so each change between the two kinds of call would load the setup again in a new process.
  - A bundle request as the first request of each process. The stylesheet attempt of the core has no entry lists to send, and the pool can still start a process with a stylesheet call. So the order cannot hold.
  - One setup for each kind of call. It breaks the requirement of one Vite server for each source root, in the section "The Vite Server" of `docs/protocol/mokly-vite-adapter.md`. The CSS and the JavaScript of one render could then also use different config values.
  - No source rule for config imports. It breaks the user's choice of 2026-11-27 that the source rule applies to each file that the config loader selects.
- **Wider fix:** D. Its record carries the exact-path decision of each workspace import on every compile path, so no consumer derives it again from the lists of the request at hand. It also covers the catalogue imports that a reused module graph keeps.
