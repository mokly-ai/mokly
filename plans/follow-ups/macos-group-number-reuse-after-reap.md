# Cleanup can signal a reused group number

- **Severity:** High. **Likelihood:** Rare. **Effort:** Large. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-26, from review finding 6 of the branch `calummoore/ci-speed-flaky-decisions-a`, as the wider fix that the branch split off, and the problem outside its scope that the finding check found.
- **Location:** `crates/mokly-platform/src/unix_process_tree/group.rs:91-117`, `crates/mokly-platform/src/unix_process_tree/outcome.rs`, and the waiters in `crates/mokly-git/src/system.rs:131-141`.
- **Reason:** The structural fix changes when the Git runner, the sidecar, and the base install reap their root process, and the branch that found it fixed only the new window.

- **Source:** Review.
- **Category:** Product bug.
- **Terms:**
  - **Process group number:** the ID of a Unix process group. It equals the process ID of the process that created the group.
  - **Process tree guard:** `UnixGroup` in `crates/mokly-platform/src/unix_process_tree/group.rs`. It signals the group of a command and each process that it finds through parent links.
- **Background:**
  - The guard sends each group signal by number. Before it does, it checks that the root process ID still names the root, and it accepts a root that is gone.
  - The Git runner reaps the root on a separate thread, so the root can be gone while the guard still signals.
  - A group number can only be reused after every process of the old group is gone. Then a new process with that ID can create a new group with the same number.
  - On 2026-11-26, the branch `calummoore/ci-speed-flaky-decisions-a` added a fallback: when macOS refuses a group signal, the guard reads the group members by number and signals each one. The same branch then made that fallback skip the members when another process now holds the root ID.
  - Two gaps remain:
    - When the root is gone and no process holds its ID, the guard still signals the group number. A new group whose leader already exited, such as a daemon after a double fork, can hold that number. This is the same on `main` before the branch.
    - Between the second root check and each member signal, a short check-then-act gap stays, like the one of the existing root check.
- **Problem:** After the root is reaped, the guard cannot prove that a group number still names the group of the command.
- **Impact if no action:** In a rare timing, cleanup can stop or kill an unrelated process of the same user.
- **Root question:** How does cleanup keep a group number reserved for its command until cleanup ends?
- **Options:**
  - **C.** Keep an owned process that reserves the group number until cleanup ends, and coordinate its lifetime with the Git, sidecar, and base-install waiters. Effort: Large.
  - **D.** When the root lookup finds no process, signal the group or its members only after a retained identity or the root confirms membership of that group. Otherwise, treat the group as gone. Orphans of a reaped root that the walk never found then lose the group signal, which changes behaviour on `main`. Effort: Medium.
  - **E.** Make the guard own the reap. Callers wait for exit with `waitid(..., WEXITED | WNOWAIT)`, the guard finishes cleanup, and only then is the root reaped. The root zombie keeps its ID, so no new group can take the number. Effort: Large.
- **Left out:** Filtering members by session ID or start time, because a new leader that calls `setsid` gets the same session number and later members can join a group.
- **Wider fix:** E. A root that stays unreaped reserves the number for every caller, with no new process.
- **Previous examples:** `a_reused_root_pid_never_receives_a_group_signal` in `crates/mokly-platform/src/unix_process_tree/_tests_/group_tests.rs` rejects a reused root ID before the first group signal. `a_refused_group_whose_leader_id_was_reused_gets_no_member_signal` in `outcome_tests.rs` covers the fallback.
- **Related:** `plans/follow-ups/macos-stop-mid-walk-orphans.md` covers orphans outside the group, which E does not reach.
- **Recommendation:** E. It closes the reuse for every caller and keeps every orphan reachable.
- **Action:** fix after merge, apply E, because it changes the reap of three callers.
