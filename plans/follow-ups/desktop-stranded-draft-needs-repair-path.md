# A complete desktop draft can get stranded

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-24, the wider fix of review finding 2 of the branch `calummoore/desktop-releases-become-latest-releases-clkn`.
- **Location:** `packages/desktop/scripts/release-assets.mjs`, the function `publishRelease`. `packages/desktop/scripts/release-promote.mjs`. The section "Drafts And Promotion" of `docs/protocol/cloud/desktop-distribution.md`.
- **Reason:** Each option changes a release rule in force: the rule that assets are never deleted, or the rule that each asset has the size that its platform job recorded.
- **Category:** Product bug.

- **Terms:**
  - **Draft:** A GitHub release that only collaborators can see. It is never GitHub's latest release, and its assets can still change.
  - **Platform job:** One leg of the `release` job of `.github/workflows/desktop-release.yml`. It builds one platform, uploads to the draft, checks its own assets, and writes a platform manifest with their names and sizes.
  - **Promotion:** The `promote` job. It checks both manifests and the draft, then makes the draft the latest full release.
- **Background:**
  - On 2026-11-24 the owner chose full desktop releases. Each release becomes latest only after the complete asset check of both platforms.
  - A platform job fails on any existing asset name, and assets are never replaced or deleted. `docs/protocol/cloud/desktop-distribution.md` states this for drafts too. On `main` before that change, the rule covered published assets only, because people can have downloaded them.
  - Sometimes GitHub stores every asset, but the job fails after that: the answer to the last upload is lost, the check read fails, the manifest upload fails, or the runner stops. A rerun then stops at the existing names. The complete draft stays a draft, and the next version is the only recovery.
  - Each GitHub release asset has a `digest`, a SHA-256 hash of the stored file. GitHub's immutable releases setting locks the assets of a published release.
  - `plans/follow-ups/desktop-promotion-manifests-expire.md` holds the direct fix, job outputs for the manifests, which covers only expiry and a failed manifest upload.
- **Problem:** A failure after a complete upload strands a draft whose assets all arrived.
- **Impact if no action:** A rare failure after the uploads needs a new version, with a new signing and notarization run.
- **Root question:** How does a draft whose assets all arrived still become latest after a later step fails, while a set that failed its own check never does?
- **Options:**
  - **A.** Job outputs for the manifests, as the direct fix item says. It covers expiry and a failed manifest upload only. Effort: Medium.
  - **B.** Save the names and SHA-256 hashes of each build before the upload, and keep that record through the rerun window. On a rerun, accept an existing complete set when each `digest` matches. Effort: Medium.
  - **C.** Stage the signed builds and their records as workflow artifacts before any release upload, and keep them through the rerun window. One job then uploads both platforms from that checked set. It moves full installers through Actions storage. Effort: Large.
  - **D.** Make GitHub's draft the only record. The promotion checks the exact fixed names, the `uploaded` state and the release flags, and reads no manifest. A platform rerun passes when its complete fixed set is already uploaded. It drops the rule that each size matches the platform job's record. Effort: Medium.
  - **E.** Make a draft repairable. On a rerun, while the release is still a draft, the platform job deletes only the assets with its own fixed names, then uploads its new build and a new manifest. A rerun then also repairs a partial upload. It reverses the rule that draft assets are never deleted. A defect in the draft check could delete a published asset, which the immutable releases setting can block. Effort: Medium.
- **Left out:** Retention alone does not help when the record was never stored. Retries of the reads inside the job leave a stopped runner and a lost upload answer. A manual publish skips the automated check that the owner's decision requires.
- **Wider fix:** E. It prevents the whole class for every failure before publication, a partial upload included.
- **Previous examples:** None found.
- **Recommendation:** B. It keeps both rules in force, because it deletes no asset and still ties each asset to its build, now by hash. E protects the release best, but it reverses the never-delete rule for drafts.
- **Action:** ask the user, because each option that closes the class changes a release rule in force, and B adds a rerun behaviour that no requirement covers.
- **Related:** `plans/follow-ups/desktop-promotion-manifests-expire.md` is the direct fix of the same finding. The answer here can replace it.
