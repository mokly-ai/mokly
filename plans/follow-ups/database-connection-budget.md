# Derive pool sizes from one connection limit

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Large. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-24, from branch `calummoore/gcp-project-cost-qz5o`, the wider fix of review finding 1.
- **Location:** `infra/terraform/modules/sql/main.tf:41`, `infra/helm/mokly-cloud/values.yaml:100`, `crates/mkc-store-pg/src/connection.rs:16`.
- **Reason:** The fix touches Terraform, the Helm chart, three binaries and the deploy goldens, so it needs its own branch after the tier change.

- **Source:** Review.
- **Category:** Product bug.
- **Terms:**
  - **`max_connections`:** the PostgreSQL limit on simultaneous client sessions. Cloud SQL sets its default from the instance memory.
  - **Store pool:** the r2d2 connection pool that `PgStoreFactory::connect` in `crates/mkc-store-pg/src/connection.rs` creates for each API pod, catalogue pod and maintenance job.
  - **Replica ceiling:** the `scaling.maxReplicas` value in `infra/helm/mokly-cloud/values.yaml`, the highest pod count that the autoscaler reaches.
- **Background:**
  - Both stable Cloud SQL instances, production and main-preview, use the tier `db-custom-1-3840`: 1 vCPU and 3.75 GB. The user chose this tier for production on 2026-11-24, to match main-preview and save cost.
  - For 3.75 GB to 6 GB instances, the Cloud SQL default `max_connections` is 100. Before 2026-11-24, production used `db-custom-2-7680`, whose default limit is 400. On 2026-11-24 the user chose to raise the limit of both instances to 160 with a `max_connections` flag in `infra/terraform/modules/sql/main.tf`. PostgreSQL keeps 3 connections for superusers, so the workload roles get about 157. The value 160 is set by hand from the counts below.
  - The chart scales `api`, `app` and `catalogue` from 2 to 6 replicas with `maxSurge: 1`. `app` uses no database.
  - Each store pool has a maximum of 8 connections. Since 2026-11-24, a pool keeps at least 1 idle connection ready. Each time a call takes the last idle connection, the pool queues one more, up to 8, also while earlier connections are still opening. So a burst, or calls made one after another, can grow the pool past the number of connections in use. Each connection closes 60 to 90 seconds after it becomes idle, the kept one included, and the pool opens a replacement in the background. A local run against Postgres 16 showed 3 busy connections grow the pool to 6, and all 6 close 90 seconds after the work ended, with 1 fresh connection left. Each API pod also holds 1 readiness connection in a separate single-connection pool (`crates/mkc-db/src/migration.rs:86`).
  - Jobs: the migration hook uses 1 connection and makes one attempt (`crates/mkc-db/src/migration.rs:47`, `backoffLimit: 0` in `infra/helm/mokly-cloud/templates/migration.yaml`). `publication-check-status` runs every 5 minutes. `billing-delivery-status` also runs every 5 minutes, but only when billing is enabled (`infra/helm/mokly-cloud/templates/maintenance.yaml:2`). `auth-prune` runs at minute 17 of each hour, `github-prune` at 02:31, and `publication-maintenance` at 02:47 (`infra/helm/mokly-cloud/values.yaml:110`). The two status jobs make one store call each, so each holds at most 2 connections. The three long jobs make many transactions one after another, so each can grow to 8. The long jobs never start at a five-minute mark, but `auth-prune` can run for 480 seconds and `publication-maintenance` up to its 600-second deadline, so one long job can overlap the two status jobs. `concurrencyPolicy: Forbid` applies only inside one CronJob. Local runs against Postgres 16 gave 2 connections for one transaction, 6 for five transactions like `auth-prune`, and 5 to 8 for 100 transactions.
  - Rollouts use `maxSurge: 1` and `maxUnavailable: 0`, with a 30-second termination grace period (`infra/helm/mokly-cloud/templates/workloads.yaml:22` and `:29`). An outgoing pod receives SIGINT, drains its requests, and keeps every open connection until its process exits. The drain usually takes under 1 second, and at most 30. The Deployment controller does not count a pod after its deletion starts, so each outgoing pod overlaps with replicas + 1 other pods.
- **Problem:** At 6 API and 6 catalogue replicas, the pools and readiness connections reach 102: 6 × 9 + 6 × 8. During a rolling update, with one outgoing pod per workload, they reach 136: 8 × 9 + 8 × 8. Each further outgoing pair adds 17, when a drain lasts longer than a new pod takes to start. The two status jobs and one long job add up to 12, so the peak is 148 with billing enabled and 146 without. In a rare case, a late `auth-prune` at 02:17 overlaps `github-prune`, which gives 152. These fit in 157. A second outgoing pair gives 165, which does not fit. But the limit is a hand-set number in Terraform, the pool size lives in Rust, and the replica ceilings live in the chart. Nothing keeps them in step, so a higher ceiling, a larger pool, or a smaller limit can push the peak past the limit without notice.
- **Impact if no action:** Today, nothing. After such a change, at high load with most pods saturated, requests wait up to 5 seconds for a connection and then fail, and the one-attempt migration hook of a deploy can fail.
- **Root question:** How do the connections that the pods and jobs of an environment can hold stay within that environment's database limit, at every replica count and every release step that autoscaling and rollouts reach?
- **Options:**
  - **A.** Keep one connection limit for each environment in a checked-in file that Terraform and `infra/helm/render-values.py` both read, as `render-values.py` already reads `infra/toolchains.json`. Terraform sets `max_connections` from it in place of the hand-set 160. The chart passes each workload and each job its pool settings, computed from the limit, the replica ceiling, the surge, the outgoing pods, and a reserve. The three binaries read those settings through `PgStoreFactory`. A Postgres test can then inject a 1-second idle timeout and wait until one connection remains, without a wall-clock bound. Effort: Large.
  - **B.** Run PgBouncer in the cluster in transaction mode, with a fixed server pool below the limit. Migrations need a direct session, because they use `pg_advisory_lock`. The catalogue's read-only role needs its own pooler. Effort: Large.
  - **C.** Set `minReadySeconds` above the termination grace period on the Deployments that use Cloud SQL, for example 35 seconds. Kubernetes then deletes the next old pod only after the previous one has stopped, so at most one outgoing pod per workload exists and 136 becomes a true limit. Each rollout step waits 35 seconds longer, about 3.5 minutes per workload at 6 replicas. Effort: Small.
  - **E.** Give the maintenance commands a one-session pool: a maximum of 1 connection and no kept idle connection, like the readiness pool in `crates/mkc-db/src/migration.rs:86`. No maintenance command makes nested or parallel store calls, so it cannot deadlock. Each job then holds exactly 1 connection, and the job allowance drops from 12 to 3. It needs the pool-settings input of A, at the five maintenance call sites: `crates/mkc-api/src/cli_maintenance.rs:47` and `:86`, `crates/mkc-api/src/cli_recovery.rs:49` and `:95`, and `crates/mkc-api/src/maintenance/factory.rs:34`. Effort: Medium alone, Small inside A.
  - **D.** When the shared limit falls, roll out the workloads sized for the new limit before Terraform applies it. Today Deploy applies Terraform before the rollout (`docs/protocol/cloud/infrastructure-promotion.md`, the promotion sequence), so old pools can exceed a lowered limit until the rollout ends, and the one-attempt migration hook can fail. This changes the promotion sequence, a requirement in force, so it needs a user decision and a protocol doc update. Effort: Large.
- **Left out:** A larger tier breaks the user decision of 2026-11-24. Cloud SQL Managed Connection Pooling needs Enterprise Plus, which also breaks that decision. Lower replica ceilings cut peak capacity, and the raised limit already covers the current ceilings. A retry in the migration hook does not help, because each old pool takes a freed connection back within 2.5 seconds. A check that only detects an overrun is a new gate, and A prevents the case. No kept idle connection in every pool would also bound the jobs, but each quiet serving pod would then open a new connection through the Cloud SQL proxy for its first request. Staggering the job schedules does not help, because the long jobs can run across a five-minute mark.
- **Wider fix:** A, with C to bound the outgoing pods, E to bound the jobs, and D for limit decreases. A tier change or a ceiling change then resizes the pools, so the mismatch cannot return.
- **Previous examples:** Main-preview has used this tier with the same ceilings and pools since PR #350, with no recorded incident.
- **Recommendation:** A with C and E. They keep the decided tier and the ceilings, and they remove the class. D waits for the user, because it changes the promotion sequence.
- **Action:** fix after merge, apply A, C and E, because they reach Terraform, the chart, and three binaries, outside the tier change.
