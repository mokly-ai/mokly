# Derive pool sizes from one connection limit

- **Severity:** Medium. **Likelihood:** Rare. **Effort:** Large. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-24, from branch `calummoore/gcp-project-cost-qz5o`, the wider fix of review finding 1.
- **Location:** `infra/terraform/modules/sql/main.tf:41`, `infra/helm/mokly-cloud/values.yaml:100`, `crates/mkc-store-pg/src/connection.rs:16`.
- **Reason:** The fix touches Terraform, the Helm chart, three binaries and the deploy goldens, so it needs its own branch after the tier change.

- **Source:** Review.
- **Category:** Product bug.
- **Terms:**
  - **`max_connections`:** the PostgreSQL limit on simultaneous client sessions. Cloud SQL sets its default from the instance memory.
  - **Store pool:** the r2d2 connection pool that `PgStoreFactory::connect` in `crates/mkc-store-pg/src/connection.rs` creates for each API pod, catalogue pod and maintenance job.
  - **Replica ceiling:** the `scaling.maxReplicas` value in `infra/helm/mokly-cloud/values.yaml`, the highest pod count that the autoscaler reaches.
- **Background:**
  - Both stable Cloud SQL instances, production and main-preview, use the tier `db-custom-1-3840`: 1 vCPU and 3.75 GB. The user chose this tier for production on 2026-11-24, to match main-preview and save cost.
  - For 3.75 GB to 6 GB instances, the Cloud SQL default `max_connections` is 100. Before 2026-11-24, production used `db-custom-2-7680`, whose default limit is 400. On 2026-11-24 the user chose to raise the limit of both instances to 160 with a `max_connections` flag in `infra/terraform/modules/sql/main.tf`. PostgreSQL keeps 3 connections for superusers, so the workload roles get about 157. The value 160 is set by hand from the counts below.
  - The chart scales `api`, `app` and `catalogue` from 2 to 6 replicas with `maxSurge: 1`. `app` uses no database.
  - Each store pool has a maximum of 8 connections. Since 2026-11-24, a pool keeps no idle minimum, so it starts no connection that no call asked for. A connection that opens in the background while the process exits can crash it in the OpenSSL exit handler. `connect` opens one connection to check the database. Each connection closes at most 90 seconds after its last call, so an idle pool ends with none. A burst can leave more connections than its peak calls in flight, because a connection that a call queued still opens after the call took a returned one, up to 8. `crates/mkc-store-pg/src/_tests_/pool_tests.rs` checks that serial calls reuse one connection. Each API pod also holds 1 readiness connection in a separate single-connection pool (`crates/mkc-db/src/migration.rs:86`).
  - Jobs: the migration hook uses 1 connection and makes one attempt (`crates/mkc-db/src/migration.rs:47`, `backoffLimit: 0` in `infra/helm/mokly-cloud/templates/migration.yaml`). `publication-check-status` runs every 5 minutes. `billing-delivery-status` also runs every 5 minutes, but only when billing is enabled (`infra/helm/mokly-cloud/templates/maintenance.yaml:2`). `auth-prune` runs at minute 17 of each hour, `github-prune` at 02:31, and `publication-maintenance` at 02:47 (`infra/helm/mokly-cloud/values.yaml:110`). Each job makes its store calls one after another, so it holds at most 1 connection. Each job may start up to 300 seconds late (`startingDeadlineSeconds`) and runs up to its 600-second deadline (`activeDeadlineSeconds`), so one long job can overlap the two status jobs. `concurrencyPolicy: Forbid` applies only inside one CronJob. In a rare case, an `auth-prune` that starts late at 02:17 overlaps `github-prune` at 02:31, which adds 1. `github-prune` ends by 02:46, before `publication-maintenance` starts.
  - Rollouts use `maxSurge: 1` and `maxUnavailable: 0`, with a 30-second termination grace period (`infra/helm/mokly-cloud/templates/workloads.yaml:22` and `:29`). An outgoing pod receives SIGINT, drains its requests, and keeps every open connection until its process exits. The drain usually takes under 1 second, and at most 30. The Deployment controller does not count a pod after its deletion starts, so each outgoing pod overlaps with replicas + 1 other pods. The next old pod goes only after a new pod passes its startup and readiness probes. Production Deploy runs took 15 to 25 seconds for each step. So in a rollout step, a second outgoing pod of a workload exists only when a drain outlasts a step, and a third only when steps are short and a pod is killed at the 30-second limit. An autoscaler change or an eviction during a rollout deletes pods outside these steps, so it can add outgoing pods too. Nothing else bounds the number of outgoing pods.
- **Problem:** These totals count every pod at its pool cap, so they are worst cases. An API pod starts its worker loops, which use the store, before it is ready, so a surge pod counts at its cap too. The scenarios at 6 API and 6 catalogue replicas, with billing enabled:
  - At rest: 6 × 9 + 6 × 8 = 102, plus 3 for jobs: 105.
  - A rollout step with one surge pod and one outgoing pod per workload: 8 × 9 + 8 × 8 = 136, plus 3 for jobs: 139, or 140 in the rare job case.
  - A second outgoing pod per workload: 153 + 3 = 156, or 157.
  - A third outgoing API pod: 165, the first total above the 157 usable connections.

  At 2 replicas, as production runs today, the worst case is about 70. But the limit is a hand-set number in Terraform, the pool size lives in Rust, and the replica ceilings live in the chart. Nothing keeps them in step, so a higher ceiling, a larger pool, or a smaller limit can push the peak past the limit without notice.

- **Impact if no action:** Today, only a rollout at the replica ceilings with every pool full and three overlapping drains goes past the limit. After such a change, at high load with most pods saturated, requests wait up to 5 seconds for a connection and then fail, and the one-attempt migration hook of a deploy can fail.
- **Root question:** How do the connections that the pods and jobs of an environment can hold stay within that environment's database limit, at every replica count and every release step that autoscaling and rollouts reach?
- **Options:**
  - **A.** Keep one connection limit for each environment in a checked-in file that Terraform and `infra/helm/render-values.py` both read, as `render-values.py` already reads `infra/toolchains.json`. Terraform sets `max_connections` from it in place of the hand-set 160. The chart passes each workload and each job its pool settings, computed from the limit, the replica ceiling, the surge, the outgoing pods, and a reserve. The three binaries read those settings through `PgStoreFactory`. A Postgres test can then inject a short idle timeout, open several connections, release them, and poll `pg_stat_activity` until none remains. r2d2 0.8 sweeps idle connections 30 seconds after the pool is built and every 30 seconds after, and a caller cannot change that rate, so the poll must cover the first sweep. The test asserts no elapsed time. Effort: Large.
  - **B.** Run PgBouncer in the cluster in transaction mode, with a fixed server pool below the limit. Migrations need a direct session, because they use `pg_advisory_lock`. The catalogue's read-only role needs its own pooler. Effort: Large.
  - **C.** Set `minReadySeconds` above the termination grace period on the Deployments that use Cloud SQL, for example 35 seconds. Kubernetes then deletes the next old pod only after the previous one has stopped, so rollout steps leave at most one outgoing pod per workload. An autoscaler change or an eviction during a rollout deletes pods without this pacing, so 136 is a limit for rollout steps only, and the reserve in option A covers the rest. Each rollout step waits 35 seconds longer, about 3.5 minutes per workload at 6 replicas. Effort: Small.
  - **E.** Give the maintenance commands a store that cannot open more than one connection: a connection that the command owns, or a pool with a maximum of 1, like the readiness pool in `crates/mkc-db/src/migration.rs:86`. No maintenance command makes nested or parallel store calls. Only the owned connection, opened on the calling thread and bounded by libpq's `connect_timeout`, also removes the maintenance commands' part of the exit race in `plans/follow-ups/r2d2-connect-races-openssl-exit.md`. A one-slot pool still opens its connection on an r2d2 worker, which a timed-out checkout leaves running. Today each job holds one connection only because the shared pool keeps no idle minimum. This makes the count hold by construction. The call sites are `crates/mkc-api/src/cli_maintenance.rs:47` and `:86`, `crates/mkc-api/src/cli_recovery.rs:49` and `:95`, and `crates/mkc-api/src/maintenance/factory.rs:34`. Effort: Medium alone, Small inside A.
  - **D.** When the shared limit falls, roll out the workloads sized for the new limit before Terraform applies it. Today Deploy applies Terraform before the rollout (`docs/protocol/cloud/infrastructure-promotion.md`, the promotion sequence), so old pools can exceed a lowered limit until the rollout ends, and the one-attempt migration hook can fail. This changes the promotion sequence, a requirement in force, so it needs a user decision and a protocol doc update. Effort: Large.
- **Left out:** A larger tier breaks the user decision of 2026-11-24. Cloud SQL Managed Connection Pooling needs Enterprise Plus, which also breaks that decision. Lower replica ceilings cut peak capacity, and the raised limit already covers the current ceilings. A retry in the migration hook does not help, because a pool whose call queued a connection keeps retrying it, so a freed connection goes back to the old pools. A check that only detects an overrun is a new gate, and A prevents the case.
- **Wider fix:** A, with C to pace the outgoing pods of rollout steps, E to bound the jobs, and D for limit decreases. A tier change or a ceiling change then resizes the pools, so the mismatch cannot return.
- **Related:** `plans/follow-ups/r2d2-connect-races-openssl-exit.md`: the owned-connection form of option E also removes the maintenance commands' part of that exit race.
- **Previous examples:** Main-preview has used this tier with the same ceilings and pools since PR #350, with no recorded incident.
- **Recommendation:** A with C and E. They keep the decided tier and the ceilings, and they remove the class. D waits for the user, because it changes the promotion sequence.
- **Action:** fix after merge, apply A, C and E, because they reach Terraform, the chart, and three binaries, outside the tier change.
