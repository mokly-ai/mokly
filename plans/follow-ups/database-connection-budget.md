# Derive pool sizes from one connection limit

- **Severity:** High. **Likelihood:** Rare. **Effort:** Large. **Confidence:** Medium. **Harder later:** No.
- **Kind:** Fix after merge.
- **Added:** 2026-11-24, from branch `calummoore/gcp-project-cost-qz5o`, the wider fix of review finding 1.
- **Location:** `infra/terraform/modules/sql/main.tf:27`, `infra/helm/mokly-cloud/values.yaml:100`, `crates/mkc-store-pg/src/connection.rs:16`.
- **Reason:** The fix touches Terraform, the Helm chart, three binaries and the deploy goldens, so it needs its own branch after the tier change.

- **Source:** Review.
- **Category:** Product bug.
- **Terms:**
  - **`max_connections`:** the PostgreSQL limit on simultaneous client sessions. Cloud SQL sets its default from the instance memory.
  - **Store pool:** the r2d2 connection pool that `PgStoreFactory::connect` in `crates/mkc-store-pg/src/connection.rs` creates for each API pod, catalogue pod and maintenance job.
  - **Replica ceiling:** the `scaling.maxReplicas` value in `infra/helm/mokly-cloud/values.yaml`, the highest pod count that the autoscaler reaches.
- **Background:**
  - Both stable Cloud SQL instances, production and main-preview, use the tier `db-custom-1-3840`: 1 vCPU and 3.75 GB. The user chose this tier for production on 2026-11-24, to match main-preview and save cost.
  - For 3.75 GB to 6 GB instances, the Cloud SQL default `max_connections` is 100. PostgreSQL keeps 3 of them for superusers, so the workload roles get about 97. No Terraform sets a `max_connections` flag. Before 2026-11-24, production used `db-custom-2-7680`, whose default limit is 400.
  - The chart scales `api`, `app` and `catalogue` from 2 to 6 replicas with `maxSurge: 1`. `app` uses no database.
  - Each store pool has a maximum of 8 connections. Since 2026-11-24, a pool opens connections on demand and keeps at least 1 idle connection ready. After a burst it can hold more connections than it used, up to 8. Each connection closes 60 to 90 seconds after it becomes idle, the kept one included, and the pool opens a replacement in the background. A local run against Postgres 16 showed 3 busy connections grow the pool to 6, and all 6 close 90 seconds after the work ended, with 1 fresh connection left. Each API pod also holds 1 readiness connection in a separate single-connection pool (`crates/mkc-db/src/migration.rs:86`).
  - Jobs: the migration hook uses 1 connection and makes one attempt (`crates/mkc-db/src/migration.rs:47`, `backoffLimit: 0` in `infra/helm/mokly-cloud/templates/migration.yaml`). `publication-check-status` runs every 5 minutes. `billing-delivery-status` also runs every 5 minutes, but only when billing is enabled (`infra/helm/mokly-cloud/templates/maintenance.yaml:2`). `auth-prune` runs every hour, and two jobs run each day. Each job makes its store calls one after another, so it holds at most 2 connections.
  - Rollouts use `maxSurge: 1` and `maxUnavailable: 0`, with a 30-second termination grace period (`infra/helm/mokly-cloud/templates/workloads.yaml:22` and `:29`). An outgoing pod receives SIGINT, drains its requests, and keeps every open connection until its process exits. The drain usually takes under 1 second, and at most 30. The Deployment controller does not count a pod after its deletion starts, so each outgoing pod overlaps with replicas + 1 other pods.
- **Problem:** When every pool is busy, demand passes the limit. At 6 API and 6 catalogue replicas, the pools and readiness connections reach 102: 6 × 9 + 6 × 8. During a rolling update, with one outgoing pod per workload, they reach 136: 8 × 9 + 8 × 8. Each further outgoing pair adds 17, when a drain lasts longer than a new pod takes to start. The jobs add up to 4, so the peak is 140 with billing enabled and 138 without. The pool size lives in Rust and the limit follows the Terraform tier, so nothing keeps them in step.
- **Impact if no action:** Only at high load, with most pods saturated, requests wait up to 5 seconds for a connection and then fail. A later tier change can lower the limit again without notice.
- **Root question:** How do the connections that the pods and jobs of an environment can hold stay within that environment's database limit, at every replica count and every release step that autoscaling and rollouts reach?
- **Options:**
  - **A.** Lower the database replica ceilings to about 3: (3 + 1 + 1) × 17 = 85, plus about 4 for the jobs. The shared `scaling` block would also limit `app`, which uses no database, unless the chart gets a ceiling for each workload. This halves peak capacity. Effort: Medium.
  - **B.** Set a `max_connections` flag of about 160 on both instances, in `infra/terraform/modules/sql/main.tf`. That covers the peak of 140, one more outgoing pair, and the 3 reserved connections. Each idle connection costs about 2 MB to 3 MB of the 3.75 GB. A flag change restarts the instance once. Effort: Small.
  - **C.** Keep one connection limit for each environment in a checked-in file that Terraform and `infra/helm/render-values.py` both read, as `render-values.py` already reads `infra/toolchains.json`. Terraform sets `max_connections` from it. The chart passes each workload and each job its pool settings, computed from the limit, the replica ceiling, the surge, the outgoing pods, and a reserve. The three binaries read those settings through `PgStoreFactory`. A Postgres test can then inject a 1-second idle timeout and wait until one connection remains, without a wall-clock bound. The flag change restarts the instance once. Effort: Large.
  - **D.** Run PgBouncer in the cluster in transaction mode, with a fixed server pool below the limit. Migrations need a direct session, because they use `pg_advisory_lock`. The catalogue's read-only role needs its own pooler. Effort: Large.
  - **E.** Set `minReadySeconds` above the termination grace period on the Deployments that use Cloud SQL, for example 35 seconds. Kubernetes then deletes the next old pod only after the previous one has stopped, so at most one outgoing pod per workload exists and 136 becomes a true limit. Each rollout step waits 35 seconds longer, about 3.5 minutes per workload at 6 replicas. Effort: Small.
  - **F.** When the shared limit falls, roll out the workloads sized for the new limit before Terraform applies it. Today Deploy applies Terraform before the rollout (`docs/protocol/cloud/infrastructure-promotion.md`, the promotion sequence), so old pools can exceed a lowered limit until the rollout ends, and the one-attempt migration hook can fail. This changes the promotion sequence, a requirement in force, so it needs a user decision and a protocol doc update. Effort: Large.
- **Left out:** A larger tier breaks the user decision of 2026-11-24. Cloud SQL Managed Connection Pooling needs Enterprise Plus, which also breaks that decision. `maxSurge: 0` alone does not reach the goal, because 102 still passes about 97. A retry in the migration hook does not help, because each old pool takes a freed slot back within 2.5 seconds. A check that only detects an overrun is a new gate, and C prevents the case.
- **Wider fix:** C, with E to bound the outgoing pods and F for limit decreases. A tier change or a ceiling change then resizes the pools, so the mismatch cannot return.
- **Previous examples:** Main-preview has used this tier with the same ceilings and pools since PR #350, with no recorded incident.
- **Recommendation:** C with E. They keep the decided tier and the ceilings, and they remove the class. B is a Small step that covers the saturated case now, if load grows before C lands. F waits for the user, because it changes the promotion sequence.
- **Action:** fix after merge, apply C and E, because they reach Terraform, the chart, and three binaries, outside the tier change.
