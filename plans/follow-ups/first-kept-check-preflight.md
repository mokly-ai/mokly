# The first kept check repeats the object check

- **Severity:** Low. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Outside the scope.
- **Added:** 2026-11-19, from the branch `calummoore/mokly-classify-memo`, a problem that its first review listed outside the scope.
- **Location:** `crates/mokly-cli/src/changes_base.rs:44`, `crates/mokly-cli/src/serve_base.rs` (`Keep::apply`), `crates/mokly-compare/src/base_retention.rs` (`KeptBase`), `crates/mokly-compare/src/base_freshness.rs` (`PreparationInputs`).
- **Reason:** The preparation sample reaches the Serve slot only through structs that existing tests build as literals, and that branch had to keep every existing test unchanged.

- **Source:** Review.
- **Category:** Performance.
- **Terms:**
  - **Kept base:** the captured base generation that Serve keeps in one slot between classifications, and reuses while its key and its freshness checks hold.
  - **Object check:** the missing-object preflight of a tree listing in `mokly-git`. It runs one `git ls-tree -l` for each 128 `.gitattributes` paths and one `git rev-list --objects --missing=print`, and it fetches missing objects from a promisor remote.
  - **`KeptListing`:** the `mokly-git` store that holds the tree listing of a commit after its object check passed. `MemoryKeptListing` keeps the SHA-256 digest of one listing.
- **Background:**
  - Before each reuse of the kept base, `ServeBase::find_kept` runs `Freshness::current_kept`. It reads the checkout identity of the base commit through `checkout_identity_with` with the `KeptListing` of the slot entry.
  - That read lists the tree again, reads `git config` and `git check-attr` again, and runs the object check only when the listing differs from the kept listing. `Keep::apply` gives each new slot entry an empty `MemoryKeptListing`.
  - The preparation of the base, `NativeBase::prepare` at `crates/mokly-cli/src/changes_base.rs:44`, samples the identity with `checkout_identity`. That read runs the object check, and it keeps no listing.
  - On the `mokly-cloud` repository (3,611 files, 434 directories), the object check runs five Git processes: four `ls-tree -l` batches and one `rev-list`, about 16 ms of process time in a shell, plus the process waits of Serve.
- **Problem:** The first freshness check after each keep finds an empty `KeptListing`. So it runs the object check again for the listing that the preparation checked a moment earlier.
- **Impact if no action:** The first edit after each base preparation pays one extra object check. The later checks of the same kept base skip it.
- **Root question:** How does the first freshness check of a kept base reuse the object check that its preparation ran?
- **Options:**
  - **A.** Change nothing. The cost is one object check for each base preparation, and a base preparation is rare next to the edits. Effort: Small.
  - **B.** Let `NativeBase::prepare` read the identity with `checkout_identity_with` and a new `MemoryKeptListing`. Carry that listing to the slot entry in `PreparedBase` and `KeptBase`, and let `Keep::apply` use it. The tests that build `KeptBase` and `PreparationInputs` as struct literals get the new field. Effort: Medium.
  - **C.** Keep one `MemoryKeptListing` in Serve state beside the slot. Pass it to `NativeBase` and `ServeBase` for each classification, and let the slot entry use the same store. The tests that build `ServeBase` and `NativeBase` as struct literals get the new field. Effort: Medium.
- **Left out:** A process-wide listing store, because the architecture rules forbid a hidden global. A second identity read in `Keep::apply`, because it only moves the object check to another point of the same edit.
- **Wider fix:** None. This is one store that its first possible read does not fill. No class of defect repeats it.
- **Previous examples:** None found.
- **Recommendation:** B. The listing then goes with the base that it describes, and the first edit after a preparation skips the object check. A is the cheaper choice when nobody measures a gain.
- **Action:** fix after merge, apply B, because it changes the preparation and retention structs outside the files of that branch, and their test literals.
