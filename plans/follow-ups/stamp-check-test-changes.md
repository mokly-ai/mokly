# Two reuse tests changed for the stamp check

- **Severity:** Low. **Effort:** Small. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-18, from the branch `calummoore/mokly-stamp-early-exit`, as an item of its implementation.
- **Location:** `crates/mokly-render/src/_tests_/stylesheet_reuse_tests.rs:100` and `crates/mokly-render/src/_tests_/bundle_reuse_tests.rs:169-184`.
- **Reason:** The task message of the change asked to keep every existing test unchanged, and no recorded decision allows these two changes.

- **Source:** Implementation.
- **Category:** Test.
- **Terms:**
  - **Input stamp:** `InputStamp` in `crates/mokly-render/src/input_stamp.rs`. It records the file digests, directory listings, assets, file identities, and directory scans of one cached bundle state or stylesheet record.
  - **Stamp check:** `InputStamp::matches`. Serve reuses a cached bundle state or stylesheet record only when its stamp check holds.
- **Background:**
  - Before the change, the stamp check read every entry of the stamp, also after the first entry that differed. On 2026-11-18 the performance orchestrator measured this cost on the `mokly-cloud` catalogue, which has about 4,600 bundle input files: about 100 ms for each Serve edit with a warm file cache, and 0.5 s to 1.8 s with a cold cache.
  - Its task message of 2026-11-18, under the user's delegation of 2026-11-16, asked for a check that stops at the first entry that differs, at all three call sites. It also said: "Keep every existing test unchanged."
  - Two existing tests pinned the full read of a failed check:
    - `a_changed_module_file_makes_every_record_of_its_context_miss_with_stamp_mismatch` asserted 551 module digests, the constant `MODULES`, for a context with one changed module. The check now reads the changed module first and stops, so the count is 1. The change set the expected value to 1. The three `StampMismatch` assertions of the test stayed.
    - `edit_reuse_keeps_stamps_and_capture_priority_while_full_reuse_rejects_omissions` mocked `SourceTree::children` in every case. `unimock` fails a test when a mocked method gets no call. In the case with a changed file digest, the check now stops before it lists the directory. The change mocks `children` only when the file digest matches. The generation assertions of the test stayed.
  - No order of the check keeps both tests unchanged. With files first, the case with a changed digest lists no directory. With directory listings first, the case with a changed listing reads no digest.
- **Problem:** The change broke a rule of its task message, and the decision maker did not accept the two test changes.
- **Impact if no action:** The two tests keep the new expected value and the new mock setup. When the decision maker wanted the old tests, the tests and the early exit disagree with that wish.
- **Root question:** Do the reuse tests follow the early exit of the stamp check?
- **Options:**
  - **A.** Keep the two test changes. No work. Effort: Small.
  - **B.** Restore the two tests, and remove the early exit, so that the check reads every entry again. Serve edits lose the saving. Effort: Small.
  - **C.** Apply A. Also move the two tests of `crates/mokly-render/src/_tests_/asset_stamp_tests.rs` from the test reference `InputStamp::current` in `crates/mokly-render/src/_tests_/stamp_reference.rs` to `InputStamp::matches`, with every assertion. Each `stamp == stamp.current(&tree)` becomes `stamp.matches(&tree)`, and each `!=` becomes `!stamp.matches(&tree)`. Their `next_call` clauses become `some_call`, as the Rust mock rule asks for changed tests. Each asset and identity test then runs the check that the product runs. It changes two more existing tests. Effort: Small.
- **Left out:** Restore the two tests and keep the early exit, because the two tests then fail, and the gate fails.
- **Wider fix:** None, because the problem is one rule of one task message, not a class.
- **Previous examples:** None found.
- **Related:** None.
- **Recommendation:** A. The changes keep every assertion about a result, and they follow the behaviour that the task message asked for. C also suits when the answer allows more changes to existing tests.
- **Action:** ask the user, because the task message asked to keep every existing test unchanged, and no recorded decision allows these two changes.
