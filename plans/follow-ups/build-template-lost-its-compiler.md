# The v5 build template has no compiler

- **Severity:** High. **Likelihood:** Rare. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-26, from the branch `calummoore/builds-give-the-template-a-git-that-9abx`, a new problem of the round 1 check of review finding 2, and review finding 6 of round 2.
- **Location:** `infra/e2b/build/e2b.Dockerfile:23` to line 24, the `apt-get purge -y --auto-remove` of the Git build packages; `docs/ops/build-template.md`, sections "Release Prerequisites" and "Live Evidence".
- **Reason:** The fix needs a new E2B template release, a credentialed probe, and a change of the build reference of main-preview, which the branch that found it was told not to do.

- **Source:** Review.
- **Category:** Product bug.
- **Terms:**
  - **Build template:** the E2B sandbox image, `mokly-build-v<N>`, in which Mokly Cloud runs the checkout, the install, and `mokly publish` of a customer repository. `infra/e2b/build/e2b.Dockerfile` defines it.
  - **Build reference:** `TEMPLATE_ID:BUILD_ID`, which starts exactly one template build. The environment app-config names it under `builds.template`.
  - **Native addon:** an npm dependency that compiles C or C++ code during install, through `node-gyp`, when no prebuilt binary fits.
- **Background:**
  - The template's base image is `e2bdev/base`, pinned by digest. It ships Debian bookworm's `build-essential`, `gcc`, `g++`, `make`, and `binutils`.
  - Release `mokly-build-v5` (build reference `tpjwc7qiz8bp7bvnpzp7:433b3d4d-1e81-4d54-8963-d62eceb3ecc8`, built 2026-11-26) builds Git 2.56.1 from source. Before the build it installs `gcc libc6-dev make libcurl4-openssl-dev libexpat1-dev zlib1g-dev`. After the build it runs `apt-get purge -y --auto-remove gcc libc6-dev make libcurl4-openssl-dev libexpat1-dev zlib1g-dev`.
  - On 2026-11-26, a check ran the Dockerfile's apt commands in a throwaway container of the pinned base. Afterwards `cc`, `gcc`, `g++`, `make`, and `ld` were missing. A simulation of the purge listed 171 removed packages. `build-essential` depends on `gcc` and `make`, so the purge removes it and `--auto-remove` removes the rest.
  - `mokly-build-v3` (build reference `1zj5lunxulyowh6ewmy3:9dffde05-0e34-4afd-91f3-ac771fd52705`) purged nothing, so it kept the compiler. v3 cannot compare, because its Git 2.39.5 rejects `git cat-file --batch --filters -Z`.
  - Main-preview builds use the v5 reference since 2026-11-26. Production has no builds.
  - The template contract in `docs/protocol/cloud/cloud-build-runner.md`, section "Template", lists `/bin/sh`, coreutils, Python 3, Git 2.43 or newer, curl, CA certificates, and Node with npm and corepack. It names no compiler.
  - The template probe, `infra/e2b/tests/assert_build_template.py`, checks no compiler.
  - The Install step of the runner runs the repository's own `npm ci` or the lockfile's package manager in the sandbox.
- **Problem:** v5 lost the compiler that v3 had. A customer repository with a native addon that has no prebuilt binary for Linux x64 glibc fails at Install.
- **Impact if no action:** Such a repository gets no cloud build on main-preview, and later on production, while the same repository built on v3. The failure shows as an install error from `node-gyp`, not as a template problem.
- **Root question:** What native build support should cloud builds give to install scripts, and how does the template add a Git that can compare without removing that support?
- **Options:**
  - **A.** In a new release, drop the package purge and keep only the source cleanup. The base already holds every package that the Git build installs (a replay installed 0 new packages and upgraded 6), so the image keeps the base's toolchain, `pkg-config`, `libtool`, the development headers, and the `libtk8.6` and `libtcl8.6` libraries that `import tkinter` needs. Verify a native dependency install and a comparison. Effort: Medium.
  - **B.** In a new release, purge only the packages that the Git build added, from a full installed-package inventory taken before the build, and keep Git's runtime libraries. On the pinned base it gives the same image as A. Effort: Medium.
  - **C.** Build Git as a versioned Debian package outside the E2B build, and install that pinned package in a new release. Effort: Large.
  - **D.** Keep v5. State in the "Template" section of `docs/protocol/cloud/cloud-build-runner.md` and in the CI guide under `docs/guides/ci/` that cloud builds supply no C or C++ toolchain, no `pkg-config`, and no development headers, so a dependency that compiles during install needs a prebuilt binary or CI publication. Repositories that compiled on v3 lose cloud builds. Effort: Small.
  - **E.** A, plus a guard: the Dockerfile installs `build-essential` and `pkg-config` by name with the other template tools, the "Template" section names a C and C++ toolchain with `make` and `pkg-config`, and the probe compiles and links a small C file and runs `make` and `pkg-config`, with a local regression. Effort: Medium.
  - **F.** Build the image outside E2B with a Docker multi-stage build: Git builds in one stage, and the final stage is the pinned base plus a `COPY --from` of the Git install. Push it by digest, and start the E2B template from that image with the SDK's `fromImage` or `fromGCPRegistry`. The release path then needs Docker or CI and a registry with credentials, against the runbook rule that the shell needs no Docker. Effort: Large.
  - **G.** Move to the Debian 13 form of the base's image lineage (`buildpack-deps:trixie`), pinned by digest. It packages Git 2.47.3 with PCRE2, gcc 14, `make`, and `pkg-config`, so the Git source build and the purge go. It changes the `e2bdev/base` rule in `docs/protocol/cloud/cloud-build-runner.md` and `docs/protocol/cloud/repository-layout.md` and the `e2b_base` check in `xtask/src/policy/build_pins.rs`, and E2B compatibility needs a check. Effort: Large.
- **Left out:**
  - A multi-stage Dockerfile through the SDK's `fromDockerfile`. `e2b@2.64.0`, the newest release, throws "Multi-stage Dockerfiles are not supported" on a second `FROM` and rejects `COPY --from`. F keeps its by-construction property.
  - Reinstall only `build-essential` after the purge. It does not bring back `pkg-config`, `libtool`, or the development headers, and A is better on every point.
  - Roll main-preview back to v3. It restores the compiler but loses every comparison.
- **Wider fix:** E. The protocol line and the probe check keep the toolchain when the cause changes shape, for example a new base digest without `gcc`. For the cause that this item shares with the second Git and the PCRE items, G removes the source build, and C moves it out of the image.
- **Previous examples:** `mokly-build-v2` broke npm by unpacking Node over the base's older npm, and its probe passed. The fix added a real `npm ci` to the probe. `plans/follow-ups/build-template-keeps-a-second-git.md` holds a second case of the base's own tools that the template changes.
- **Related:** `plans/follow-ups/build-template-keeps-a-second-git.md` and `plans/follow-ups/build-template-git-lacks-pcre.md` need a new release too, so one release can carry all three fixes. Option D of the second-Git item uses a minimal Debian 13 image without a compiler, so it keeps this loss unless it adds E or uses G.
- **Recommendation:** E. It restores what v3 had, and one contract sentence and one probe check keep the toolchain from disappearing again without a failed probe, as it did in v5.
- **Action:** ask the user, because E changes a requirement of the runner protocol, adds a probe check, and needs a credentialed template release.
