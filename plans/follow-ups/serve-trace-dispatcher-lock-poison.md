# One mock panic fails every serve trace test

- **Severity:** Medium. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-22, from CI run 45082370564 of pull request #481, an unrelated flaky test in the Repository job.
- **Location:** `crates/mokly-cli/src/_tests_/serve_trace_tests.rs`, `collect_lines`, which installs a scoped `tracing` dispatcher with `with_default`; `crates/mokly-cli/src/_tests_/extraction_trace_tests.rs:72`, the test that panicked first; the `tracing-core` 0.1.36 dependency, `src/callsite.rs:548` and `:552`.
- **Reason:** Nobody reproduced the failure, so its suspected source is not confirmed, and the next step needs a user decision.

- **Source:** Implementation.
- **Category:** Test.
- **Terms:**
  - **Trace capture:** `collect_lines` and its callers `capture`, `capture_cache`, and `capture_lines` in `serve_trace_tests.rs`. Each installs a `tracing` subscriber with a `Timings` layer for one test, and the layer holds `Unimock` clones of the terminal and the clock.
  - **Unimock:** the mock library (version 0.6.8 in `Cargo.lock`). It panics when the original instance of a mock is destroyed on a thread other than the one that created it.
  - **Dispatcher lock:** `LOCKED_DISPATCHERS`, the global `RwLock` of `tracing-core` 0.1.36 that holds a weak reference to every registered dispatcher. A thread that panics while it holds the lock poisons it for the whole test process.
- **Background:**
  - On 2026-11-22, the Repository job failed in CI run 45082370564, attempt 1, job 137393220541, on GitHub-hosted `ubuntu-24.04`, for pull request #481 at commit `de8e97a20`. That pull request changed only TypeScript, its tests, and plans, no Rust.
  - The failed command was `cargo test --locked -p "mokly-*" -p xtask`, in the test binary of `mokly-cli --bin mokly`: `test result: FAILED. 181 passed; 24 failed`.
  - The first failure: `serve_trace::extraction_trace_tests::a_built_cache_entry_records_extract` panicked at `unimock-0.6.8/src/lib.rs:992:13` with "Original Unimock instance destroyed on a different thread than the one it was created on. To solve this, clone the object before sending it to the other thread."
  - Then 23 more tests of the same binary panicked at `tracing-core-0.1.36/src/callsite.rs:552:62` or `:548:55` with "called `Result::unwrap()` on an `Err` value: PoisonError { .. }". They are `serve_services::eager_startup_tests::eager_source_starts_before_the_head_bundle_and_a_failed_head_drains_it` and 22 tests under `serve_trace::`: the extraction, render store, reuse, serve, sidecar stop, sidecar, and stylesheet trace tests.
  - Line 552 is `LOCKED_DISPATCHERS.write().unwrap()` in `register_dispatch`, and line 548 is `LOCKED_DISPATCHERS.read().unwrap()` in `rebuilder`. So after the first panic, every later dispatcher registration in the process failed.
  - Rerun outcome: the rerun of the failed jobs, attempt 2 of the same run, was cancelled when the branch merged `main` at `9639d0a5c`. The run of the new head `8e270a1c6`, run 45085570588, passed every job, Repository included. The same suite also passed on the workspace machine that built the change.
  - The last four `main` CI runs before the failure, 45068050659, 45052207991, 45024657501, and 45019307395, had no Repository failure.
  - Suspected source: a race with a concurrent test inside the dispatcher lock. It is a hypothesis, and no reproduction confirms it:
    - `register_dispatch` runs `dispatchers.retain(|d| d.upgrade().is_some())` while it holds the write lock. Each `upgrade` creates a short-lived strong reference to the subscriber of a registered dispatcher.
    - When another test drops its own trace capture at that moment, the thread in `register_dispatch` can hold the last reference. That subscriber, with its `Unimock`-backed layers, is then destroyed on the wrong thread, inside the lock.
    - The panic of the `Unimock` thread check then unwinds while the write lock is held, and it poisons the lock.
    - The panic message names an original instance. The capture layers hold clones, so which original the destruction reached is not known.
  - `CaptureReleased` in `collect_lines` (commit `70c05622e`, pull request #323) already waits for a subscriber that another thread releases. It does not cover a destruction that panics inside the dispatcher lock.
- **Related:** `plans/follow-ups/poisoned-captured-pool.md`: another lock poison that turns one test failure into many, in `crates/mokly-render`. The causes differ.
- **Problem:** One panic in a trace capture poisons the global dispatcher lock, so it fails every later test of the `mokly` binary that registers a dispatcher. A healthy Repository run can then fail.
- **Impact if no action:** The Repository job, and so `Required CI`, can fail on a healthy change, and the developer must rerun it.
- **Root question:** What work should follow the unreproduced dispatcher-lock failure of the serve trace tests?
- **Options:**
  - **A.** Change nothing, and rerun a failed job. Effort: Small.
  - **B.** Reproduce the failure by repeating `cargo test -p mokly-cli --bin mokly` with many test threads. Confirm or reject the suspected source. Then make the trace capture safe: for example, give no subscriber a mock whose destruction can panic, or keep each capture's subscriber out of the reach of other tests. Add no retry. Effort: Medium.
- **Left out:**
  - A retry of the tests. The flaky-test rule of the `testing` skill forbids a retry.
  - A fix before a source is named. The same rule needs a named source before a fix.
  - Only two approaches are real, because each fix that rests on evidence needs the reproduction of B.
- **Wider fix:** B, when the named source is the capture's subscriber, because a fix there covers every trace test of the binary.
- **Previous examples:** None found in the `main` CI runs above.
- **Recommendation:** B. One panic fails 24 tests at once, so a recurrence costs a full rerun of the Repository job.
- **Action:** ask the user, because no reproduction confirms the suspected source, and the testing skill sends an unknown source to the user.
