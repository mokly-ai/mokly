# Centralized build titles escape reverse parity

- **Severity:** Low. **Effort:** Medium. **Confidence:** High. **Harder later:** No.
- **Kind:** Needs decision.
- **Added:** 2026-11-04, from the second-pass options check of the review of branch `conductor/follow-ups-app-build-copy-and-comments`.
- **Location:** `apps/app/src/viewer/build-stage.tsx:36` and `:72`, `apps/app/src/viewer/build-copy.ts:196-200`, `docs/mockups/src/_tests_/app-owners.ts:562-565` and `:600-603`, `docs/mockups/src/_tests_/app-state-titles.ts:98-118`, `docs/mockups/src/_tests_/app-parity.ts:135-159` and `docs/protocol/cloud/product-mockups.md:94-96`.
- **Reason:** Every option changes a protocol requirement or protected parity test code, and the recommended option adds a stricter completeness check that needs explicit user approval.
- **Source:** Review.
- **Category:** Test.

- **Terms:**
  - **Parity suite:** The mockup tests in `docs/mockups/src/_tests_/` that compare each drawn product screen with the App source files that render it.
  - **Owner row:** One entry of the `owners` table in `docs/mockups/src/_tests_/app-owners.ts`, which names the owner files that answer for one drawn screen.
  - **Forward copy check:** `labelDivergences` in `docs/mockups/src/_tests_/app-parity.ts`, which requires each drawn label and state title as a string literal in the owner files of its screen.
  - **Reverse title check:** `stateTitleDivergences` in the same file, which requires each state title that an owner file announces to appear on a screen that names that file.
  - **Centralized title:** A state title that a copy module holds as a value and that a component reads through a member expression, such as `buildStageCopy.unavailable`.
- **Background:**
  - On 2026-11-04 the user chose one copy owner for three App viewer components: the build card, the build address's stage and the publishing card. Their copy moved into `apps/app/src/viewer/build-copy.ts`, the build-stage titles included.
  - `docs/protocol/cloud/product-mockups.md:94-96` requires the state title comparison of the parity suite in both directions. One direction finds a title that the catalogue draws and the product does not write. The other finds a title that the product announces and no declared screen draws.
  - `stateTitlesWritten` in `docs/mockups/src/_tests_/app-state-titles.ts:98-118` finds a title only as a string literal in the title prop of a listed state component, such as `StateMessage` or `StageError`. Its comment at lines 94-96 leaves every other title to "the file that does decide it".
  - The reverse title check, at `docs/mockups/src/_tests_/app-parity.ts:135-159`, runs that extraction only over owner files.
  - On `origin/main`, the owner rows of `product/viewer/standalone/build` and `product/viewer/standalone/build/unreadable` named `viewer/build-stage.tsx`. That file wrote both titles as literal `title` props.
  - The move changed two things, and either change alone takes both titles out of the reverse title check:
    - `build-stage.tsx:36` and `:72` now read `buildStageCopy.unavailable` and `buildStageCopy.unreadable`.
    - Both owner rows now name `viewer/build-copy.ts` and `viewer/stage.tsx` in place of `viewer/build-stage.tsx`.
  - Both strings now live in the `buildStageCopy` record at `build-copy.ts:196-200`. That file is an owner file, but it renders no state component.
  - `ownerViolations()` at `app-parity-owners.ts:76-83` rejects an owner file that writes no label that its screens draw. So `build-stage.tsx` cannot return to the owner rows.
  - The loss stops at these two titles. The check still reads "No publications yet" and "No publication yet" from `apps/app/src/viewer/stage.tsx:47` and `:127`. "Loading build" is a pending label, which the reverse title check never read.
  - Explicit tests still cover the current behavior, and they pass. `apps/app/src/_tests_/build-route.spec.ts:14-41` asserts both App titles and their recovery. The test at `docs/mockups/src/_tests_/build-address.test.ts:21` asserts the stage title or pending label of each unresolved build address drawing that `build-drawings.ts` lists. The forward copy check finds each drawn title in `build-copy.ts`.
  - The user decided on 2026-11-03 that a follow-up decision does not block a merge. So the copy move does not wait for this question.
- **Problem:** The reverse title check no longer finds "This build is unavailable" and "This build couldn’t load". Neither is a literal in a JSX title prop now, and `build-stage.tsx` is no longer an owner file. A future centralized title escapes the check in the same way, so the check is narrower than the both-directions rule.
- **Impact if no action:** No drawing is missing now, and no visible bug exists. A state title that the App gains through a copy module can lack a drawing without the existing reverse check reporting it.
- **Root question:** How should mockup checks cover the centralized build-stage titles?
- **Options:**
  - **A.** Accept the narrower automatic coverage. Keep the explicit browser and mockup tests and the forward copy check. Update `docs/protocol/cloud/product-mockups.md` to state the narrower rule, so that each future centralized title needs explicit coverage. This weakens a stated requirement. Effort: Small.
  - **B.** Declare an explicit group of state titles in the copy owner, such as the two titles of `buildStageCopy`. Let the owner metadata in `app-owners.ts` expose that group to the reverse title check. Keep the current assertions. A title added to the declared group then enters the existing comparison. Implement it in a separate change after approval. Effort: Medium.
  - **C.** Make `stateTitlesWritten` resolve an imported title expression, such as `buildStageCopy.unavailable`, back to its string value. This keeps the production copy shapes, but adds source-analysis code to maintain. C alone cannot restore coverage. `build-stage.tsx` is no longer an owner file, so the check never reads its title expressions, and `ownerViolations()` rejects the file as an owner. Effort: Medium.
  - **D.** Complete C with an App-wide caller scan. Read the state component titles in every App source, as `announcerViolations()` in `app-parity-owners.ts` already does. Resolve each title with the TypeScript checker, which `docs/mockups/src/_tests_/deterministic-source-parser.ts` already uses. Credit each value to the owner file that declares it, here `build-copy.ts`. This restores both titles with no declaration, and it also reads `copy.title` in `publish-card.tsx`. A title that a function returns as `string` still escapes in silence. It costs a second TypeScript program over the App sources, its run time, and a first run that also reads older titles. Effort: Medium.
  - **E.** B, plus a completeness check. Keep the declared titles in `app-owners.ts`, not in the copy owner, in the way that `SentenceDeclaration` at `app-owners.ts:784-785` names a shared constant. Then production code does not change for a test. Scan every App source, as `announcerViolations()` already does. Fail on each state component title that is not a literal, a forwarded prop or a declared title. The failure message tells the developer to declare the title. This is a stricter check, so it needs the user's explicit approval. It also needs declarations for `copy.title` at `publish-card.tsx:41` and `:91`. The scan also reads older App titles, which can need more declarations or allowlist lines. The same completeness check also works with D. Effort: Medium.
- **Left out:** Move the titles back into JSX literals: it breaks the user's choice of one copy owner, which names the three build-stage strings. Add a new lint: a lint cannot compare the App's titles with the drawings, so it fails the goal. A lint that forbids non-literal titles also reverses the copy move. Collect the titles that the browser tests render: it sees only the states that a test opens, so an untested new title still escapes. Require a branded title type in every state component: it changes every state component and each caller for a Low test gap. E closes that gap in test code. Change nothing: the check stays narrower than the protocol rule, and no decision records why. Every option keeps the visible text and the chosen copy owner, and it lands in a later change.
- **Wider fix:** E, not B. B must know each declared group, so it is a direct fix. E still reports a title whose shape changes, such as a new copy record, a function or a local alias.
- **Previous examples:** `buildTitle` in `apps/app/src/viewer/build-copy.ts` already returned the build card's titles from a module without JSX at `origin/main` commit `9bed6b43`, so the reverse title check never read them.
- **Recommendation:** E. It restores both titles through the declarations of B and makes the next undeclared title fail, while B alone does not remove the stated impact. The first recommendation was B.
- **Action:** ask the user, because option E adds a stricter completeness check, and every fix changes protected parity test code that no approved scope covers.
